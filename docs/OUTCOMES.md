# 外の数字 (Outcome measurements)

`pytest` が 788 件通ることは、**自分で書いた主張を自分で確かめた**という
意味しかない。`verify_gate_recall.py` も同じで、検知器も検査事例もこちら

このファイルは、**こちらが書いていないもの**に対して測った数字だけを置く。
5 つのリポジトリは他の目的のために他の誰かが書いたもので、質問の答えは
このファイルより前から存在している。だから数字が下がることがある。それが
このファイルの存在理由で、下がらない数字は測っていないのと同じ。

再測定:

```bash
python scripts/measure_outcomes.py \
  tukemen-rgb/sidra-ai=. \
  tukemen-rgb/site=/workspace/tukemen-rgb/site \
  tukemen-rgb/creater-yard=/workspace/tukemen-rgb/creater-yard \
  tukemen-rgb/Fg=/workspace/tukemen-rgb/Fg \
  tukemen-rgb/marketing=/workspace/tukemen-rgb/marketing
```

5 リポジトリが checkout されていない環境では、足りないものを明示して
落とす。4 本で測った数字を 5 本の数字の隣に並べない。

### 下限ができた（2026-08-19 ループB）

この表の数字は**下がっても何も止めなかった**。誤検知率が
`check_gate_regression.py` を持つ前と同じ状態だったので、同じものを作った。

```
python scripts/check_answerable_regression.py \
  tukemen-rgb/sidra-ai=. tukemen-rgb/site=<path> \
  tukemen-rgb/creater-yard=<path> tukemen-rgb/Fg=<path> \
  tukemen-rgb/marketing=<path>
```

下限は 4 本（回答可能 **6** / 直接語 6 / 言い換え **0** / 識別力 +15.0pt）。
混ぜた 1 本にしないのは、直接語と言い換えは壊れ方が違うので片方の改善が
もう片方の崩壊を隠すから。識別力にも下限があるのは、**鈍くなることで
満たせる下限は下限ではない**から。部分 checkout では数字を出さずに拒否する。

**最初の下限（7 / 6 / 1）は古いコーパスに固定されていて、範囲を製品と
揃えた直後に green な main に対して赤くなった。**再固定したのが上の値。
言い換えの下限 1 は「黙ってゼロになるのを防ぐ」という主張自体は正しかったが、
**根拠にした 1 件は製品が取り込まない `.tsx` への当たり**で、実在の
システムが一度も到達していない水準だった。今の下限 0 は何も守らないので、
**守っていないことを毎回出力させる**（消すと二度と誰も問わなくなる）。
1 問でも通ったら「下限を上げること」と出る。

**まだ CI では走っていない。**4 本の clone が要り、CI の job は
`Same-SHA offline verification` と名乗っているため（E 節で要判断）。
それまでは retrieval / chunker / tokenizer / security gate を触った回が
手で走らせること。**とくにゲートを締めた回**: 索引から文書が消えれば
回答可能率は落ちる。安全側の変更が製品側で何を失うかは、この 2 つを
両方走らせて初めて見える。

**結論は 2 つあり、両方とも本当のことである。**

1. **効果は出た。** 回答可能 7→9、MRR 0.307→0.463、識別力も +27.8→+33.3pt と

### コーパスが製品と違っていた（今回の修正）

取り込みの範囲が 2 か所に別々に書かれていて、食い違っていた。

| | 対象 | 5 本の合計 |
|---|---|---:|
| 製品（`list_docs_paths`） | README と `docs/**` | 94 文書 |
| 測定（`measure_outcomes.py`） | checkout 内の全テキストファイル | 520 文書 |

（`.py` 205・`.tsx` 145・`.ts` 24・`.json` 18・`.sh` 11）。業務の質問に
アプリのソースが返っていたのはそのためで、`site/SPEC.md` は rank 10 にいた。

**製品が持たないコーパスに対する数字は、悲観的な数字ではなく別のシステムの
数字である。**範囲の定義を `sidra_ai/ingestion/scope.py` に 1 本化し、製品と
測定の両方がそれを参照するようにした。`tests/test_documentation_scope.py` が
両者の一致を固定する。

範囲を揃えたら、**製品側の穴が見えた**。`site/SPEC.md` と
`creater-yard/SPEC.md` はリポジトリ直下にあり、README は読むのに
その隣の仕様書は読まない、という恣意的な欠落だった。18 問のうち 4 問の

直下から再帰すると `app/` や `node_modules/` まで歩き、1 回の取り込みが
数千リクエストになる）。追加コストは 1 リポジトリあたり 1 リクエスト。

なお測定側にはまだ 2 つの過小評価が残る。commit / PR / issue は実際の索引の
一部だが checkout からは読めない。`max_items_per_source`（50）も測定側には
無い。どちらも「実際より低く出る」方向なので、数字を良く見せてはいない。

### 取り下げた理由

`src/sidra_ai/evals/outcome_questions.py` は `answer_marker` を全問ぶん
そのまま書いてある。そういうファイルである。同時にそれは allowlist 済み
リポジトリの中の `.py` ファイルなので、**コーパス走査がそれを拾って索引に
入れていた**。検索器は各マーカーを「それを宣言しているファイル」の中に見つけ、
rank 1 を返す。接地チェック（`marker_present_in_corpus`）も同じ理由で通る。

この状態を sidra-ai だけの checkout で走らせると、**Fg も site も 1 つも
checkout されていないのに 18/18 が rank 1、回答可能率 100.0%、MRR 1.000**
と出た。根拠として返っていたチャンクは 18 問すべて
`src/sidra_ai/evals/outcome_questions.py` だった。

- **回答可能率・MRR・直接語・言い換え** — 5 本 checkout 時も答案が索引に
  入っていたので、本物の文書で当たったのか答案で当たったのか区別できない。
  100% のうちどれだけが本物かは、**再測定するまで分からない**。
- **対照・識別力** — こちらは確実に汚染されている。対照は「他リポジトリの
  マーカーが紛れ込んだか」で測るが、他リポジトリのマーカーも全部あの 1 ファイル
  に入っている。あのチャンクが返るたびに対照が立つ。
- **到達率 90.3%** — 答案ファイルの混入という点ではほぼ影響が無かった
  （除外されるのは 1 文書だけ）。ただしこの数字自体はのちに別の理由で
  差し替わっている（コーパスが製品のものではなかった。上記参照）。

**再測定は 5 リポジトリを checkout してから行うこと。**開発環境からでも

| 依頼 | 文書が書く操作 | hard の帯 |
|---|---|---|
| 釣りゲーム | SPACE / クリック | 0.12 |
| キャッチゲーム | ← → / マウス | 0.12（受け皿幅） |

構成は **`game.html` が単一画面である事実**を書く。タイトル画面もリザルト
画面も無いので、3 画面のフローを書けば仕様ではなく願望になる。無い画面は
「まだ無いもの（増やすなら実装と同時に）」に分けた。

**あらすじと配役は空欄のままにした。** 物語は「この作品は何についてか」という
主張で、生成すれば読み手が最も確かめない場所に捏造した意図を置くことになる。
空欄には理由ラベルを付けてあり、ローカルモデルがあれば `with_prose` で上書き
できる（空文字を返せばラベルが残る）。

計器の設計が肝で、**「書けたか」ではなく「この制作固有か」を数える**。長さで
測れば汎用の散文が満点を取り、見出しで測れば置き換え前の版が満点を取る。
ディスクを読み、各ステージが自分の操作キーか難易度数値を持つときだけ 1 と
数える。**置き換え前の 〔未記入〕 版が 0 になることをテストで固定した**——
それを検出できない計器に意味は無い。

## 2026-08-26: 生成した素材を、ページが実際に読んでいる

`creation_assets_generated` **unmeasurable → 1**（判定器 exit 0）。

テンプレごとに `target` / `marker` の 2 枚をプロシージャル SVG で生成し、
`assets/` に置いて game.html が相対パスで参照する。

**パレットは閉じている。** 塗りは DESIGN.md §2 のトークンのみ。検査は SVG を
**パースして renderer が実際に塗る色を列挙**する——正規表現なら子ノードに
仕込まれた色を見落とす。生成器が色を発明すると、§2 が防ごうとしている
「2 つ目のデザインシステム」を 1 ファイルずつ再建することになる。個別には
どれも正常に見えるので、集合で見るまで誰も気づかない種類の劣化。

**乱数は依頼文からの seed。** `hash()` はプロセスごとに salt されるため
digest を使った。同じ依頼が同じバイト列を返さなければ、**自分の文書が説明
している絵と違う絵**がプロジェクトに入る（C-996 の文書は art を説明する）。

**計器は 2 つ折り。** ディスクに SVG があってもページが読まなければ飾りで、
ページが参照しても書かれていなければ壊れた画像。**どちらも片側だけの検査は
通る**（ファイルは在る／ページは描画される）ので、参照の成立まで 1 つの数字
で見る。

**落ちても遊べる。** 画像が decode 済みでなければ元の矩形に落ちる。assets/ を
空にしても失うのは見た目だけで、プレイは失わない。単体ページ（非プロジェクト）
は sprites 未指定で従来どおりの単一ファイルのまま——`assets/` を一切含まない
ことをテストで固定した。loopback 固定の運用で、単体成果物が兄弟ファイルを
取りに行き始めたら、それは C-991 が塞いだ穴の再発になる。

## 2026-08-26: 文法だけで勝つチャンクを止めた — answerable 13→14、混入は 4→3 問

C-1008 の修正。CJK 文字バイグラムは助詞・語尾を内容語と同じ重みで数える。
しかも IDF はそれを**助長する**——散文のコーパスでは「〜はどこですか」という
文の形のほうが内容語より珍しいからだ。結果、質問しか書かれていない
インタビュー票が「質問の形が一番似ているチャンク」として勝ち続けていた。

### 直し方: 項ではなくチャンクに掛ける

BACKLOG の指示は「助詞・語尾バイグラムの重み付け側で解くこと」。最初に
書いたのは素直な解釈——**全ひらがなの項を一律 0.25 倍**——で、これは
判定器に落とされた。

| 案 | answerable | 他リポジトリ混入 | discrimination | 判定 |
|---|---:|---:|---:|---|
| 変更前 | 13/38 | 4 問 | +23.7 pt | — |
| 一律 0.25 倍（項別） | 15/38 | 9 問 | **+15.8 pt** | **exit 2 / 不採用** |
| 内容語 0 のチャンクだけ 0.25 倍 | 14/38 | **3 問** | **+28.9 pt** | exit 0 / 採用 |

一律案は製品の数字（13→15）を上げる代わりに、**安全側の
`answerable_discrimination` を下限 +15.0 のすぐ上まで削っていた**。
5 リポジトリは同じ事業の話をしているので、内容語の一致が強まるほど
「他所のもっともらしい答え」が top5 に入る。それを承知で採るのは
「前進」ではないので捨てた。

採った案は条件が 1 つ違うだけで結果が逆になる。**内容語に 1 つも当たって
いないチャンクに限って**、文法バイグラム分の得点を 0.25 倍にする。内容語に
当たったチャンクの文法得点は満点のまま——だから、まともに当たっている
チャンク同士の順位は変わらず、混入はむしろ 4→3 問に減った。

### 0 ではなく 0.25 である理由

0 にすると、文法しか当たらないチャンクの得点はちょうど 0 になり
`score > min_score` で落ちる。それは同じ測定で**既に否定された案 (b)**
（「内容語が一致しなければ返さない」＝正解 12 問中 4 問を道連れ）に
なってしまう。分数にしてあるのは、順位を下げるだけで消さないため。

  モデルが居ない・遅い・壊れている・悪意がある、どれでもページは遊べる。
- **渡るのは文言だけ。** 依頼文はそのまま上げるが、検索した本文は
  一切送らないし返ってもこない。「遊べるページに索引 DATA は入らない」
  という保証はそのまま立っている。
- **失敗の形は 1 つだけ。** バックエンド不達・JSON でない散文・400 字の題・
  作品名・マークアップ — 全部 `None` を返し、モデル無しのページと**同一の要約**
  になる。挙動の族ではなく 1 つの挙動として考えられる。
- **echo は呼ぶ前に断る。** 既定バックエンドは検索結果の抜粋を返す器で、
  その出力は題ではない。訊いて捨てる実装だと、重みの無い checkout 全部で
  毎リクエスト 1 生成を捨てることになる。断りは呼び出し前に置いた。

禁止語のリストは **2 本持たない**。`games._TRADEMARKS` を遅延 import して
導出し、モデル特有の綴り（`zelda` / `TETRIS` など）だけを足す。最初は
コピーして持っていて、**テストが実際に食い違い（`kirby` / `nintendo` /
`dragon ball` の 3 語）を検出した**ので導出に変えた。2 本のリストは必ず
片方だけ古くなり、古くなる方は誰も読んでいない方である。

商標改名の注記も守った。「ドラゴンボールのゲームを作って」は題を差し替えて
理由を tagline に印刷するが、モデルの一言でそこを上書きすると**改名した理由が
黙って消える**。改名されたページはモデルの題だけ受け取り、説明は自分のものを
残す。

計器は本物の生成器に fake バックエンドを注入して**両方向**を見る。答えた
モデルの題が**保存済み HTML に届く**こと、6 種類の失敗が `plain` と同じ要約・
同じ playable のままであること、backend 呼び出しがちょうど 1 回であること。
配線を外すと 1 → **0** に落ちることを確認してから提出した（「題が変わった」
だけを見る計器は、モデルを無視して自分で改名する生成器を通してしまう）。

資料（deck）側は同型のまま残っている。C-1029 として起票した。**ゲームの 1 を
資料の証拠には使わない。**

## C-1034: 戦闘だけ音が大きい（2026-08-30 18:4x UTC ループA）

`creation_combat_loudness` unmeasurable → **1**（`product_metrics.py --compare` exit 0）。

§6 観察 4 の実測は「戦闘窓は -13.8〜-16.5 LUFS に集中し、会話場面より明確に
大きい」。つまりあの映像は**戦闘で違う音を鳴らしているだけでなく、大きく
鳴らしている**。`combat(on)` を 1 つ足し、戦闘中は全効果音のゲインを 1 段上げる。

**係数について正直に。**知識ベースには戦闘窓の LUFS はあるが**会話窓の値が
無い**ので、正確な dB 差は導出できない。×2（約 +6 dB）は「明確に大きい」の
控えめな代用値であり、判定器が見ているのは**この定数ではなく、段が実在して
ページに届き、消音の下に留まること**である。

段が壊れる形は 3 つあり、全部「録音する AudioContext」を差した node で
実測する（source を読んでも見えない）。

1. **宣言されただけでゲインに届かない。**calm 0.24 → loud 0.48 を実測。
2. **operator の消音を上書きする。**M は戦闘中も勝つ。上書きできる音量機能は
   設計を着たバグなので、消音を上書きさせる改変で 1 → **0** を確認した。
3. **割れる。**上限 0.9 を超えない。割れる戦闘は大きいのではなく壊れている。

4 つ目は source では**原理的に**見えない——「呼ばれない条件の裏にある
`combat(true)`」。なので実際にページを遊ばせ、戦闘を持つ型（duel / kaiju /
shooter）が**自分で**段を上げること、持たない型（fishing / catch / puzzle）が
**上げないこと**まで見る。パズルに `combat(true)` を足す改変でも 1 → **0**。

**冒険は「合格」に数えていない。**adventure は「敵が 120px 以内のときだけ」に
した——常時オンより良い設計で、静かな区間があるから戦闘が大きく聞こえる。
ところが現行のブラウザ差し替えではそこまでページを運転できない（hero 座標が
NaN になる既存の性質で、この変更とは無関係）。**計測を楽にするために設計を
落とすことはしない**ので、節はそのままにしてギャップを C-1035 として起票した。
埋まるまで adventure は数字に入れない。

## C-1035: 計器の穴を埋めに行って、ページが死ぬバグを見つけた（2026-08-30 19:4x UTC ループA）

`creation_combat_verified` unmeasurable → **7**（全テンプレート、判定器 exit 0）。

C-1034 で「adventure は敵が近いときだけ音が大きい」節を入れたが、ブラウザ
差し替えではそこまで運転できず、計器の穴として C-1035 に起票していた。
**原因は差し替えの不足ではなく、製品のバグだった。**

`moveEnemies` は敵とプレイヤーの距離 `d` で割って追跡方向を出す。

```
en.dx=(hero.x-en.x)/d*ESPEED
```

**真上に重なると `d===0`** で速度が NaN になり、以後 `solid(NaN,..)` が
`rooms[room][NaN]` を読んで**例外を投げる**。ループはそこで止まり、ページは
**無言で死ぬ**——負けたのでも勝ったのでもなく、ただ動かなくなり、リロード
しか戻る道がない。

**実プレイで到達しうる。**接触ダメージのノックバックは `hero.x-=en.dx*14` で
hero を**敵の進行方向に沿って**押すので、重なりは偶然の産物ではない。

修正は `const towards=d||1`。重なっている間は追うべき方向が存在しないので
その場に留まり、数行下の接触ダメージが起きる——それが正しい挙動である。

これで adventure を運転でき、「敵を hero の上に置くと段が上がる」ことを実測
できた。7 型すべてで音量規則（段・消音・上限・そのテンプレ自身の使い方）が
実測済みになった。

**数字の出方について正直に。**C-1035 は「対象テンプレ 6→7」を約束していたが、
旧「6」は計器コード内の集合であって記録された数字ではない。差分を偽装せず、
`creation_combat_verified` を新設して **7** として出した。

そして記録しておくべきことは数字ではない方だ。**計器の穴を埋めに行ったら、
埋めるべきだったのは計器ではなくゲームだった。**「動かして判定する」を
続けている理由がこれで、grep していたら永遠に見つからなかった。

## 場面が変われば色が変わる（C-1036, 2026-09-01 ループA）

`creation_scene_palettes` **unmeasurable → 2**（判定器 exit 0）。adventure の
3 部屋と kaiju の 3 phase が、それぞれ別の基調色で塗られるようになった。

§7 観察 5-6（社長提供の映像を機械抽出した色彩設計）が言っていたのは 2 つ。
**場所ごとにアクセント 1 系統**で場面を塗り分けること、そして**全編で最も
明るい色をクライマックスに予約する**こと。SIDRA は前者が無く（3 部屋が同一
パレット、kaiju は全 phase 同一背景）、後者は概念ごと無かった。

実装は `src/sidra_ai/creation/scene.py`。**テーマ色の置き換えではなく変換**に
してあるので、「テーマを指定すると配色が変わり、指定しなければ変わらない」は
壊れていない——4 テーマすべてで場面差が残ることを実測して確かめた。

**測って初めて分かったことが 2 つあり、どちらも設計を変えさせた。**

**1. 明度の刻みを HSL の lightness で取ると、紙テーマで森が山場より明るく
なる。** sRGB では明るさの大半を色相が運ぶ（緑の係数 0.7152 に対し青は
0.0722）ので、同じ lightness でも緑はマゼンタより明るい。既定テーマのように
暗い土台なら気づかない。**相対輝度を目標に置き、その輝度になる lightness を
二分探索で解く**方式に変えて、全テーマ・全色相で「最も明るい場面が最終部」が
成立するようにした。

**2. 明度を加算で上げると、壁と床の明度差が潰れる。** 祭壇で床/壁比が
**1.04**（無加工 1.23）まで落ちていた。§4 の「地形は形と明度で読ませる」を
装飾のために削るということで、これは進捗ではない。変換を
**(輝度 + 0.05) に対する一律の乗算**——WCAG のコントラスト比の定義そのもの——に
変えた結果、床/壁比はどの場面でもテーマ既定値と一致する（gameyard 1.23 /
paper 1.32 / terminal 1.63 / dusk 1.35）。**場面パレットは雰囲気だけを運び、
可読性の予算は 1 も使っていない。**

計器が噛むことは 3 通りの破壊で確認した。パレットを 3 場面同一にする → 0、
最大明度を中間 phase に移す → 0、加算方式に戻す → 0（床/壁比の低下として
検出）。いずれも復元して 2 に戻る。

**どちらの発見も、暗いテーマ 1 つで確認していたら出なかった。**明度の逆転は
紙テーマでしか起きず、コントラストの喪失は最も明るい場面でしか起きない。
「4 テーマ × 2 型を全部走らせる」を計器側の既定にしてあるのはこのためで、
既定テーマだけ緑なら通ってしまう変更だった。

## 直せる余地を人に残す（C-1113, 2026-09-02 ループA）

`creation_param_panel` unmeasurable → **9**（判定器 exit 0）。9 型すべての
生成ページが「調整」フォームを同梱するようになった。難度プリセット、

## 絵は後から差し替えられる（C-1116, 2026-09-02 ループA）

`creation_sprite_slots` unmeasurable → **4**（判定器 exit 0）。目標に書かれて
いた 9 には届いていない。**届かせなかった理由の方が中身がある**ので先に書く。

**規約。** ページが描く絵はすべて `sprite(name, ...)` を通り、その `name` は
役割つきのスロットとして宣言される。埋めるのは `assets/<name>.<ext>` を
置くだけ。手続き生成の `.svg` は優先順の**最後**なので、後から置いた PNG が
必ず勝つ。ファイルが無ければテンプレが元から描いていた平面図形のまま遊べる。
この 3 つ目があるので、画像モデルが 1 つも無い今日の状態で出荷できる。

**両方向を node で走らせて確認している。** decode 済みの画像があるときは
`drawImage` が走り平面図形は描かれない、decode されないときは fallback の
`fillRect` が走る。「常に fallback するローダ」は前者で落ちる。

**9 に届かせなかった判断。** 目標の 9 は「全テンプレに画像スロットがある」を
前提にしていた。しかし kaiju / racing / platformer / puzzle には**絵を持たない
理由が既にコードに書かれている**——怪獣は全身像を出さないシルエット、レースは
周回ごとに画面全体を塗り直すので焼き込まれた色が浮く、足場は縁の明度差で
着地位置を読ませる、パズルは色そのものが機構。ここに絵を差せば 8 になるが、
それは**設計判断を数字と交換すること**なので取らなかった。

**副産物の発見。** duel は書かれた日から `sprite('fighter')` を呼んでいたのに、
充填する生成器が一度も存在しなかった。宣言と呼び出しの照合で出た。ただし
この呼び出しは手続き描画の体の**下**に敷く任意の絵なので、生成器を足しても
ほぼ見えない。埋めるのではなく「未充填スロット＋理由」として宣言した。
9 型すべてで宣言と呼び出しが一致していることは判定器の前提条件にしてあるので、
新しいテンプレが宣言なしに絵を足すことはできない。

画像モデルの導入自体は社長の PC の話なので、E 節「要判断: ローカル画像モデルを
入れるか」に選択肢とコストを添えて置いた。受け皿だけ先にある状態。

## 60 秒で必ず区切りが来る（C-1104, 2026-09-02 ループA）

`creation_round_within_60s` unmeasurable → **9**（判定器 exit 0）。起動して
1 入力だけ与え、あとは無操作で 70 秒回した実測。9 型すべてが区切りに達する。

**なぜ必要だったか。** §8 事実 1。終わりのないページは「無限に遊べる」のでは
なく「置くタイミングが無い」。fishing と catch には state machine そのものが
無く、「1 回どのくらい？」に答えが存在しなかった。残り 7 型も上限は無かった。

**数えるのは遊んだ時間で、壁時計ではない。** タイトル画面と一時停止は
このラッパより手前でフレームを止めるので、放置しても 60 秒は減らない。
タイトルに 10 秒置いてから始めても区切りはちょうど 60 秒、と計器で確認した。

**テンプレ自身の終了が優先。** 9 型中 4 型は自前で終わる（duel 8.5s /
shooter 25.6s / kaiju 26.0s / racing 52.5s）。クロックが知る必要があるのは
「まだ遊んでいる state」だけで、その表は判定器がスクリプトと突き合わせるので、
テンプレが新しい負け方を足しても表が黙って古くなることはない。

**区切ってもループは止めない。** hitstop と同じで最後のフレームを保持した
ままバナーを出す。落としたループは戻せない——これは計器の合格条件にしてある。

**実装中に自分のバグを 1 件出して直した。** 最初の版は「テンプレが live に
戻ったら解除」にしていた。ところがクロックが鳴るのは**テンプレがまだ
終わっていない**ときなので state は常に live で、バナーは 1 フレームしか
出なかった。ソースを読んでいたら気づかない。ページを動かして初めて出た。
解除は明示的な再スタートだけ、に直した。

## 負けの瞬間に形をつける（C-1105, 2026-09-02 ループA）

## スコアが買えるのは色だけ（C-1109, 2026-09-03 ループA）

`creation_cosmetic_unlock` unmeasurable → **9**（判定器 exit 0）。9 型すべてで、
遊んだ累計に応じて「見た目だけ」の色が開き、**開いた色はゲームの中身を
1 ピクセルも動かさない**。目標は 1 型だったが、共通プリアンブルなので
全型に付いた。

**この項目の中身は「解放がある」ではなく「解放が不公平でない」ことである。**
時間の行き先を作る一番ふつうのやり方＝速い機体を解放する、は、後から来た人
ほど弱い状態で遊ばされるという意味でゲームを壊す。だから測っているのは
「解放の存在」ではなく **性能不変** のほうで、測り方はこうした:

同じシード・同じ入力・**同じ累計**で 2 回実プレイし、片方だけスキンを着せる。
2 つの走行は「**同じ図形を違う色で**」描かなければならない。描画ジオメトリ
（fillRect / drawImage / fillText の引数）を 1 本のハッシュに畳み、スコア列を
別に取り、色集合をまた別に取る。ジオメトリとスコアが完全一致し、色集合だけが
違えば合格。スキンが速さ・大きさ・湧き間隔のどれかに触れていれば、ジオメトリ
が動いて落ちる。

**判定器の穴を 1 つ見つけて、数字ではなく判定器を直した。** 5 通りの破壊で
0 に落ちることを確認する途中、「スキンが速さを 1.2 倍する」破壊だけ
adventure が落ちなかった。理由は判定器の側にあった——連打プレイヤーは村
（room 0）から出られず、adventure は敵を room 1 以降にしか置かないので、
`ESPEED` が一度も動かない。**トレースはプレイヤーが触った軸しか見られない。**
方向キーを 4 方向に増やしても、握る時間を 8 倍にしても、村から出なかった。

そこで同じ主張を別の経路でもう一度立てた。組み上がったページを読み、
**スキンに触れている呼び出しが色（`skinAccent`）・加算（`skinBank`）・
告知（`skinNews`）の 3 か所しかない**ことを検査する。触れる場所が 3 つしか
無いなら、スキンは数字に届きようがない——プローブが気付いたかどうかに
関係なく。この検査は同じ破壊で 9 型すべてが落ちる。**2 つの検査は違う壊れ方
をする。それが 2 つある理由である。**

**値段は型ごとに実測した。** 1 個の共通値段（例「200pt」）にすると、puzzle は
1 ラウンドで 3 色開き、adventure は永久に 1 色も開かない——1 ラウンドのスコアが
2 桁違うため。`SKIN_UNIT` は各型を 60 秒フルに連打させて実際に出たスコアで、
値段はその 3 / 10 / 25 倍。テストが同じ測定を毎回やり直すので、得点の桁が
変わった型が値段を置き去りにすることはない。

**確認した破壊は 5 通り**（それぞれ 9 → 0）:
スキンが速さを変える／加算をやめる／最初から全部開いている／選んだ色が
ページに届かない／1 ラウンドで開く値段にする。

**通信は 0。** 累計も選択も `localStorage` のみ。`fetch` も URL も無いことを
テストと判定器の両方で確認している。端末情報も送らないし、そもそも読まない。

## 貼れる 1 行、ただし何も明かさない（C-1110, 2026-09-03 ループA）

`creation_share_text` unmeasurable → **9**（判定器 exit 0）。9 型すべてで、
ラウンドが終わるとページ自身のボタン（と C キー）が
`今日の釣り 2026-09-03 🐟🐟🐟🐟🐟 釣果 132 自己ベスト` の 1 行を
クリップボードへ載せる。目標は 1 型。

**測っているのは「ボタンがある」ではなく「載った文字列の中身」である。**
判定器は実際にラウンドを終わらせ、結果が出た画面でページ自身のボタンを押し、
クリップボードに届いた文字そのものを読む。そこに**無いこと**を確かめるものが
3 つある——URL（`http` / `://` / `www.` / `@` / localhost / `file:`）、
その人自身のもの（依頼文の語・生成タイトル・端末情報）、そして盤面

**日付だけが例外で、それが例外である理由が全体の設計そのものである。**
日替わりのスタンプは貼っても安全だ——その日に遊んだ全員が同じ値を持つから。
依頼由来のシードはその正反対なので、決して載せない。日替わりが切のときは
日付も出ない（出れば「共有された盤面」という主張が意味を失う）。

**判定器が検出しない破壊を 1 つ、意図的に残した。** 日替わりシード自体を
行に足す破壊は 9 のままだった。これは穴ではない: その値は同じ日の全員に
共通で、ネタバレでも個人情報でもない。**検出しないと決めたことを書き残す
ほうが、検出したふりをするより判定器を長持ちさせる。**

**確認した破壊は 5 通り**（それぞれ 9 → 0）: URL を足す／依頼由来シードを
足す／生成タイトルを頭に使う／絵文字の本数を固定にする／ラウンド中でも
コピーできるようにする。

**途中で既存の不具合を 1 つ見つけて直した。** `roundBank` は「1 ラウンドに
1 回だけ」の作りで、それを開け直す経路が無かった。開いたままやり直す型
（duel / racing / shooter）では、2 回目のラウンドが始まってもリザルト帯が
1 回目のスコアを出し続けていた——そしてコピーする行も同じ数字を主張して
いた。ラウンドが live に戻ったら銀行を開け直すようにし、`afterRestart` を
計器に足して 3 型で固定した。**C-1110 を作っていなければ見つからなかった
C-1106 の欠陥である。**

**DESIGN.md §3 の絵文字禁止に触れたので、触れた事実を残す。** 既存テストは
「ページ HTML に U+1F000 超の文字が 1 つも無いこと」を見ていた。§3 の趣旨は
`docs/OUTCOMES.md` に書かれているとおり**「絵文字をインターフェイス
アイコンに使わない」**であり、知識ベース §8 事実 7 は逆に、Wordle の拡散は
**絵文字グリッド＋URL 無し**で起きたと記録している（この項目はその事実の
実装である）。趣旨は保ったまま、例外を 1 か所に絞って**より狭く** pin し
直した: ページ内の U+1F000 超の文字はその型の共有マークだけで、しかも
**ページ中にちょうど 1 回**——コピー行を組み立てる spec の中——しか現れて
はならない。ボタンにもラベルにも見出しにも 1 つ出れば落ちる。
**緩めてはいないが、既存の検査に手を入れたことは数字より先に書いておく。**

## 開いて 1 回押せば遊べ、次からは押さなくていい（C-1111, 2026-09-03 ループA）

`creation_instant_start` unmeasurable → **9**（判定器 exit 0）。9 型すべてで、
初回はブリーフィングが出て**どのキー / タップでも 1 入力・1 フレーム（17ms）**で
操作可能になり、2 回目以降は**無入力でそのまま**遊べる。

**両立させるほうを選んだ。** §8 事実 8（説明・登録・ワンクッションは離脱要因）と
C-1033 のブリーフィング開始画面は正面から衝突する。片方を捨てれば数字は動くが、
三行は「操作の説明そのもの」であり、目標を誰も読んでいないゲームは
意図して遊ばれていない。だから捨てずに分けた——**初回は news、2 回目は障害物**。

**「どのキーでも」は嘘だったと、測って分かった。** `P` はタイトル画面でも
一時停止キーとして先に処理され、`GATE==='title'` では `gateTogglePause()` が
即 return するので、**P を最初に押した人には何も起きなかった**。
判定器の入力リストに P を入れていなければ気付かないままだった
（`test_the_inputs_tried_include_the_ones_that_were_special` はこの理由を残すための
テストである）。タイトル中の P は他のキーと同じ扱いにした。

**音は分離した。** 開始の押下は AudioContext を解錠するジェスチャでもあった。
自動スキップにはジェスチャが無いので、そこで音を鳴らせばブラウザに拒否され、
「音の無いゲーム」だと学習させてしまう。`gateGesture()` を `gateStart()` から
切り離し、スキップ後は**最初の実入力まで解錠を遅らせた**。判定器は
「無入力で開いた直後はまだ鳴っていない」ことと「1 入力で鳴るようになる」ことを
両方見る。

**スキップは既定であって、取り上げではない。** 調整パネルの
「毎回ブリーフィングを見る」を入れれば、2 回目以降も三行が出る。
判定器はこの戻り道も測る（戻せなくする破壊で 0 に落ちる）。

**確認した破壊は 6 通り**（それぞれ 9 → 0）: P をタイトルでも一時停止に戻す／
2 回目もゲートを閉じる／初回のブリーフィングを飛ばす／ジェスチャ前に音を鳴らす／
パネルから戻せなくする／入力後にもう 1 フレーム待たせる。

呼びながら全フレームを握りつぶすことは実際にできる（閉じているゲートが
まさにそれをしている）。数えているのは**テンプレ自身のコールバックが
受け取ったフレーム数**である。

## 部品化: 測ったら前提のほうが違っていた（C-1114, 2026-09-03 ループA）［記録］

**判定器 exit 1（NO MOVEMENT）。動いた数字は無い。それが正しい結果である**——
設計文書とリファクタであって、外の誰かに届く変化ではない。ここに書くのは
数字ではなく**測定**である。

**9 テンプレ 1024 行のうち、2 つ以上に完全一致で現れる非自明な行は 27 行。**
しかも上位はすべて基盤だった: canvas ハンドル（9/9）、種つき `rand()`（7/9）、
HUD のフォントと色（7/9）。§9 学び (3) が名指しした 4 種のメカニクス
（移動・衝突・スコア・敵行動）のうち、**そのまま持ち上げられる形で重複して
いたのは 1 つだけ**——x 方向の操舵で、kaiju・racing・shooter・platformer が
独立に 4 回書いていた。4 つの違いはキーの綴り・速度・余白だけ、つまり引数。

**残り 3 種が共有されていない理由が、この項目のいちばんの発見である。**
「まだ抽出していないから」ではない。**共有できる形になっていないから**だ。

- **座標系が 2 つある。** catch と fishing は 0..1 の正規化座標、他 7 つは
  ピクセル。落下物の衝突を 1 部品にするには、どちらかを書き直すしかない。
- **「世界の中の物」の形が 3 通りある。** `{x,y,vx,vy,r,hp}`（敵）、
  `{x,y}`（落下物）、`{x,y,got}`（宝石）。3 つの形に衝突部品は書けない。
- **ループの形が 2 つある。** catch と fishing には `state` も `reset()` も
  無い。ラウンドを終わらせる部品は、この 2 つに対して呼ぶ先が無い。

**したがって「部品を組み合わせて新ジャンル」は抽出作業ではなく、先に契約を
決める作業である。** 契約なしに抜き出すと、抜き出した元の 2 テンプレでしか
使えない部品置き場ができる。**この結論は、部品を書き始める前に測ったから
出た。**

**PoC は契約を 1 つだけ決めた。** 部品はキー状態を**ページ側**から読む——
テンプレ private の `keys` マップからは読まない（キーを private に持つ
テンプレは、そもそも他と組み合わせられない）。その上で `partsSteerX` を
racing と kaiju に載せ替えた。**キー・速度・余白は 1 つも変えていない。**

**載せ替えなかった 2 つを、わざと残した。** shooter は A/D も受けるので
載せ替えるとキーの意味が変わる。platformer は canvas 幅ではなくレベル幅で
端を決めている。どちらも単純置換では済まない。そして残したおかげで、
**同じツリーの中に「前」がある**: 実測で部品の移動回数は kaiju=170・
racing=1629 に対し、shooter=0・platformer=0。**部品が動かしていることが、
使っていないテンプレとの対比として観測できる。**

**次の順序は文書に書いた**（`docs/research/mechanics-parts.md` §5）:
座標 → エンティティ → ループ → それから初めて新ジャンル。各段階の条件は
同じで「既存の判定器の数字が 1 つも落ちないこと」。**1〜3 を飛ばして 4 を
やると、部品ではなく 10 個目のテンプレが増えるだけである。**

## 3D を、ライブラリを同梱せずに（C-1115, 2026-09-03 ループA）

`creation_game_templates` 9 → **10**。加えて共有計器 **14 本が 9 → 10**
（触って遊べる／音／開始画面／ブリーフィング／戦闘音圧／調整パネル／60 秒区切り／
失敗演出／リザルト導線／最初の 10 秒／スキン／共有文／即時開始／全部入り）。
判定器 exit 0。

**「外部 CDN に依存せず」が設計を決めた。** 項目はその検証を求めていたので、
実測で答える: three.js 最小化版は約 600KB、生成ページは現在 47KB。
**1 つの固定カメラのために全アーティファクトが約 14 倍**になり、しかも
シーングラフ・マテリアル・ローダ・WebGL バックエンドのどれもこのゲームは
呼ばない。固定カメラは数学が小さい場合である——奥行きで割り、奥から手前へ描く。
既存の 2D コンテキスト上に**約 100 行**で足りた。ページは 47KB → **49.8KB**。
これは妥協ではない: **固定カメラで three.js に呼ぶものが無い。** 代わりに
諦めたのは動くカメラが要るものすべてで、フル 3D 自動生成は元から範囲外
（§9 事実 1）。

**後から書いたテンプレが、先に書かれた部品を使った最初の例になった。**
操舵は C-1114 の `partsSteerX` を呼んでいる。部品はワールド座標でも
ピクセルでも同じように働く——**部品は自分がどの空間に居るかを知らない**、
というのが C-1114 で決めた契約の最初の実証である。

**測って直した欠陥 1 件。** 最初のゲートを x=0 に固定していた。C-1108 の
masher——うろつくだけで前進しない新規プレイヤー——は到達時に中央に居ないので、
**1 つも抜けなかった**（実測 0）。catch の初回投下と同じ扱いにして、最初の
ゲートだけ手前 90 でプレイヤーに寄るようにした。以降は全部プレイヤーの腕。

**判定器の限界を 2 つ見つけた。どちらも数字ではなく判定器を直した。**

1. `creation_cosmetic_unlock` が 9 → **0**。marble は奥行きで陰影を付けるので
   コンテキストに `rgb(255,138,61)` を渡す。**色は画面に出ているのに、文字列
   比較が「描かれていない」と言った。** `canonical_colour()` を入れて
   色として比べるようにした。破壊（玉を灰色で描く）で 10→0 を確認。
2. `creation_game_juice` が 1 → **0**。全テンプレに `shake(`/`hitstop(`/
   `burst(` の literal を要求する grep だった。marble の唯一の停止は敗北で、
   それは C-1105 の `failBeat`（＝3 つの束）が担う。**grep を通すためだけに
   2 個目の hitstop を足すのは、重みではなく水増しである。** 規則を
   「直接、または failBeat 経由」と正しく言い直した。保証は落ちていない——
   `creation_fail_beat`=10 が**実プレイで**揺れ・ヒットストップ・粒子・音を
   全型で観測している（grep より強い証拠）。破壊（failBeat を外す）で 1→0 を確認。

**一度 exit 2 が出た。** 上の 2 件が同時に落ちた状態で `--compare` は
REGRESSED を返した。**手順どおりマージせず**、数字ではなく判定器を直してから
やり直した。**13 本が 9→10 に増えていても、2 本落ちていればマージしない。**

**確認した破壊は 4 通り。** うち 1 つ（ゲートだけ差し色を外す）は **10 のまま**
だった——玉がまだ描いているので「差し色が描かれている」という主張は成立して

## 「同じ盤面」を、種ではなく盤面で測る（C-1119, 2026-09-03 ループA）

`creation_daily_seed` 1 → **10**（判定器 exit 0）。目標は 3。
10 型すべてで、日替わりを入れると**依頼文が違っても同じ日は同じ盤面**になる。

**直した対象は 2 型だが、この項目の本体は判定器の作り直しである。**

`catch` の落下位置と `fishing` の帯の位置を seeded `rand()` に載せ替えた。
fishing は**乱数を 1 つも使っていなかった**——帯は常に中央 0.5——ので、
種で決まる盤面がそもそも存在しなかった。今日の釣り場は日ごとに変わる。

**そして、素直に作った判定器は壊しても落ちなかった。** 最初は seed 値を
型ごとに比べる形にした。fishing の帯を 0.5 固定に戻しても、catch を
`Math.random` に戻しても、**10 のままだった**。理由は明白で、`SEED` は
**読まれていなくても全ページが束縛している**からである。
**C-1118 が見つけたのと同じ穴を、自分の新しい判定器で作り直していた。**

**描いたものを比べる形に変えた。** 同じ日・違う依頼文で描画ジオメトリが一致、
翌日は不一致、切れば依頼ごとに不一致。加えて 2 つの仕掛けで「種で決まるのか
偶然で決まるのか」を分離した:

1. **走行ごとに `Math.random` の系列を変える。** 種から決まる盤面はどちらの
   系列でも同じものを描き、偶然から決まる盤面は描かない。**これが catch の
   Math.random を検出する唯一の方法だった。**
2. **reduced-motion で回す。** 粒子は `Math.random` を使い、しかも半数の型で
   入力なしに勝手に発火する。最初はこれで 10 型中 4 型が「同じ日なのに違う盤面」
   と出た——**盤面ではなく粒子の差を測っていた**。C-1020 が「reduced で減るのは
   装飾だけ」を保証しているので、そこで測れば盤面だけが残る。

**確認した破壊は 4 通り**（それぞれ 10 → 0）: fishing の帯を固定／catch を
Math.random に戻す／日替わり種を日付非依存にする／切っても日替わりが効く。
**最初の 2 つは作り直す前の判定器では検出できなかった。** それが作り直しの
根拠であり、記録に残す理由でもある。

**教訓を 1 行で。** 「種が同じか」は「盤面が同じか」ではない。
**束縛されているだけの値を比べる判定器は、何も測っていない。**

## パネルにある軸は、言葉でも回る（C-1117, 2026-09-03 ループA）

`creation_revision_axes` unmeasurable → **8**（判定器 exit 0）。
言葉で回せる軸は 3（難易度・テーマ・タイトル）から **7 軸**（＋帯・差し色・
今日の挑戦・ブリーフィング）になり、帯は増減の両方向を別に数えて 8。

**塞いだ隙間はこれである**: C-1113 が全ページに 6 つのつまみを付け、
C-1112 の語彙は 3 軸のままだった。**スライダーは動かせるのに、言葉では
届かない軸があった**——これは §9 が記録する「もう一度頼んで別物を受け取る」
失敗の、ひとつ下の階層である。

**言葉が回すのは「ページが開いたときの値」にした。** パネルの既定値と
ゲーム本体のトークンを同じ schema から引くので、**パネルの表示と実際の挙動が
食い違えない**。速さだけは別軸にしていない——難易度ラダーが速さそのものであり、
2 つ持てば「速く」の意味が食い違うからである（項目の指示でもある）。
難易度が動いた回は帯もラダーから読み直す。古い帯を残すと、同じページについて
2 つの主張が並ぶ。

**判定器を 2 度作り直した。5 通りの破壊のうち 1 つしか効かなかったからである。**

- **帯の「増やして」を消しても落ちなかった** → 減る方向しか試していなかった。
  両方向を試すようにした。
- **sidecar から panel を消しても落ちなかった** → 1 回しか修正していなかった。
  **連鎖**（別の軸を回したあと、前の軸が残っているか）を見るようにした。
  これは項目の核心そのもので、それを測っていなかった。
- **`tuneFlag` が schema の既定値を無視するようにしても落ちなかった**
  → **宣言された既定値を読んでいた**。実際にページを走らせて
  `roundFacts().daily` と `gateFacts().skipped` を聞くようにした。
  **C-1119 で学んだのと同じ誤りを、1 時間後に別の場所でもう一度やった**:
  宣言は製品の事実ではない。

**効かなくてよい破壊が 1 つあった。** `_MAKE_VERBS` の veto を外しても
「難しいゲームを作成して」は revision にならない——調整語の要求
（「難しい」は「難しく」ではない）が先に却下するからである。service は
revision を先に試すので veto は無意味ではないが、**観測可能な挙動は変わらない**。
効かない破壊は、効かない理由まで確かめてから「効かなくてよい」と書く。

**副産物**: `tuneFlag` が schema の既定値より呼び出し側のハードコードを
優先していた（`dailyOn()` の `false`）。schema はそのページについて生成器が
決めたことなので、こちらが優先されるべきである。直した。
