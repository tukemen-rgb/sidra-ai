# 外の数字 (Outcome measurements)

`pytest` が 788 件通ることは、**自分で書いた主張を自分で確かめた**という
意味しかない。`verify_gate_recall.py` も同じで、検知器も検査事例もこちら

このファイルは、**こちらが書いていないもの**に対して測った数字だけを置く。
5 つのリポジトリは他の目的のために他の誰かが書いたもので、質問の答えは
このファイルより前から存在している。だから数字が下がることがある。それが
このファイルの存在理由で、下がらない数字は測っていないのと同じ。

再測定:

```bash
python scripts/measure_outcomes.py \
  tukemen-rgb/sidra-ai=. \
  tukemen-rgb/site=/workspace/tukemen-rgb/site \
  tukemen-rgb/creater-yard=/workspace/tukemen-rgb/creater-yard \

  tukemen-rgb/marketing=/workspace/tukemen-rgb/marketing
```

5 リポジトリが checkout されていない環境では、足りないものを明示して
落とす。4 本で測った数字を 5 本の数字の隣に並べない。

### 下限ができた（2026-08-19 ループB）

この表の数字は**下がっても何も止めなかった**。誤検知率が
`check_gate_regression.py` を持つ前と同じ状態だったので、同じものを作った。

```

  tukemen-rgb/sidra-ai=. tukemen-rgb/site=<path> \
  tukemen-rgb/creater-yard=<path> tukemen-rgb/Fg=<path> \
  tukemen-rgb/marketing=<path>
```

下限は 4 本（回答可能 **6** / 直接語 6 / 言い換え **0** / 識別力 +15.0pt）。
混ぜた 1 本にしないのは、直接語と言い換えは壊れ方が違うので片方の改善が
もう片方の崩壊を隠すから。識別力にも下限があるのは、**鈍くなることで
満たせる下限は下限ではない**から。部分 checkout では数字を出さずに拒否する。

**最初の下限（7 / 6 / 1）は古いコーパスに固定されていて、範囲を製品と
揃えた直後に green な main に対して赤くなった。**再固定したのが上の値。
言い換えの下限 1 は「黙ってゼロになるのを防ぐ」という主張自体は正しかったが、
**根拠にした 1 件は製品が取り込まない `.tsx` への当たり**で、実在の
システムが一度も到達していない水準だった。今の下限 0 は何も守らないので、
**守っていないことを毎回出力させる**（消すと二度と誰も問わなくなる）。
1 問でも通ったら「下限を上げること」と出る。

**まだ CI では走っていない。**4 本の clone が要り、CI の job は
`Same-SHA offline verification` と名乗っているため（E 節で要判断）。
それまでは retrieval / chunker / tokenizer / security gate を触った回が
手で走らせること。**とくにゲートを締めた回**: 索引から文書が消えれば
回答可能率は落ちる。安全側の変更が製品側で何を失うかは、この 2 つを
両方走らせて初めて見える。

#### 続報: 軽い手は 3 つとも効かなかった（08-19 ループB が実測）

C 節の指示どおり、埋め込みモデルを検討する前に軽い手を測った。

| 手法 | 言い換え | 直接語 |
|---|---:|---:|
| 何もしない（基準） | 1/7 | 7/11 |
| 疑似適合フィードバック（局所, 8 設定） | 0〜1/7 | **5〜7/11（悪化）** |
| コーパス由来シソーラス（PMI 共起, 5 設定） | 0〜1/7 | 7/11 |
| 文書単位で引いてから章を選ぶ | 正解文書が top-5 に 1/7 | — |

`--diagnose` で理由が出た。**言い換え質問と正解チャンクが共有する語は
20 語中 1〜5 語**で、中身は「いる」「てい」「しま」「ので」といった活用の
断片である。7 問中 4 問は正解が **200 位以内にすら入らない**。
クエリ拡張は「質問が既に言っていること」を増幅する仕掛けなので、
質問が一度も触れていない語彙へは橋が架からない。**BM25 に渡せる信号が無い。**

同義語辞書を手で書けば数字は上がる。だがそれは**答えを読んで辞書を書く**
ことで、この文書の上半分で取り下げた「答案が索引に入っていた」誤りと
同じ構造になる。やらない。→ E 節「ローカル埋め込みモデルを入れるか」。

#### 直接語の外し方は別物 → 原因は検索器ではなくコーパスだった

`--diagnose` で、直接語の外し 4 問のうち 3 問が **rank 6 / 11 / 12** と
top-5 のすぐ外にいて、上位に `.tsx` / `.sh` / `.py` が割り込んでいた
（業務の質問に `deploy/healthcheck.sh` が返る）。順位の問題に見えたので
検索器の重み付けを疑ったが、**BM25 の実装に問題は無かった**
（k1=1.5 / b=0.75 / 文書長正規化 / IDF、いずれも教科書どおり）。

原因は**測っているコーパスが製品のものではなかった**こと。次節。

### コーパスが製品と違っていた（今回の修正）

取り込みの範囲が 2 か所に別々に書かれていて、食い違っていた。

| | 対象 | 5 本の合計 |
|---|---|---:|
| 製品（`list_docs_paths`） | README と `docs/**` | 94 文書 |
| 測定（`measure_outcomes.py`） | checkout 内の全テキストファイル | 520 文書 |

測定側のコーパスの **81.9% (426/520) は製品が一度も取り込まない文書**だった
（`.py` 205・`.tsx` 145・`.ts` 24・`.json` 18・`.sh` 11）。業務の質問に
アプリのソースが返っていたのはそのためで、`site/SPEC.md` は rank 10 にいた。

**製品が持たないコーパスに対する数字は、悲観的な数字ではなく別のシステムの
数字である。**範囲の定義を `sidra_ai/ingestion/scope.py` に 1 本化し、製品と
測定の両方がそれを参照するようにした。`tests/test_documentation_scope.py` が
両者の一致を固定する。

範囲を揃えたら、**製品側の穴が見えた**。`site/SPEC.md` と
`creater-yard/SPEC.md` はリポジトリ直下にあり、README は読むのに
その隣の仕様書は読まない、という恣意的な欠落だった。18 問のうち 4 問の
根拠が `site/SPEC.md` にある。直下を読むようにした（**降りては行かない** —
直下から再帰すると `app/` や `node_modules/` まで歩き、1 回の取り込みが
数千リクエストになる）。追加コストは 1 リポジトリあたり 1 リクエスト。

なお測定側にはまだ 2 つの過小評価が残る。commit / PR / issue は実際の索引の
一部だが checkout からは読めない。`max_items_per_source`（50）も測定側には
無い。どちらも「実際より低く出る」方向なので、数字を良く見せてはいない。

### 取り下げた理由

`src/sidra_ai/evals/outcome_questions.py` は `answer_marker` を全問ぶん
そのまま書いてある。そういうファイルである。同時にそれは allowlist 済み
リポジトリの中の `.py` ファイルなので、**コーパス走査がそれを拾って索引に
入れていた**。検索器は各マーカーを「それを宣言しているファイル」の中に見つけ、
rank 1 を返す。接地チェック（`marker_present_in_corpus`）も同じ理由で通る。

この状態を sidra-ai だけの checkout で走らせると、**Fg も site も 1 つも
checkout されていないのに 18/18 が rank 1、回答可能率 100.0%、MRR 1.000**
と出た。根拠として返っていたチャンクは 18 問すべて
`src/sidra_ai/evals/outcome_questions.py` だった。

- **回答可能率・MRR・直接語・言い換え** — 5 本 checkout 時も答案が索引に
  入っていたので、本物の文書で当たったのか答案で当たったのか区別できない。
  100% のうちどれだけが本物かは、**再測定するまで分からない**。
- **対照・識別力** — こちらは確実に汚染されている。対照は「他リポジトリの
  マーカーが紛れ込んだか」で測るが、他リポジトリのマーカーも全部あの 1 ファイル
  に入っている。あのチャンクが返るたびに対照が立つ。
- **到達率 90.3%** — 答案ファイルの混入という点ではほぼ影響が無かった
  （除外されるのは 1 文書だけ）。ただしこの数字自体はのちに別の理由で
  差し替わっている（コーパスが製品のものではなかった。上記参照）。

### 直した内容

1. `EXCLUDED_FROM_CORPUS` で答案ファイルをコーパスから外した。
2. 根拠チャンクは**その質問が対象とするリポジトリのもの**でなければ
   hit にしない。マーカーの写しがどこかにあっても接地しない。
3. 採点できた問が 0 のとき、`0.0%` ではなく `測定不能` と出す。
   0/0 を率として出すと「検索器が壊れた」に読めるが、実際には
   コーパスが無いだけである。
4. `tests/test_outcome_corpus_isolation.py` で 1〜3 を固定した
   （修正前は 4 件とも落ちる）。

**再測定は 5 リポジトリを checkout してから行うこと。**開発環境からでも
`git clone --depth 1` で 4 本とも取得できる（上の「測れた経緯」）。
1 本でも欠けたまま出た数字を、5 本で測った数字の隣に置かないこと。

### 埋め込みモデルを変えても答えは 1 問も増えない（2026-08-20 実測・ループB）

同一コーパス・26 問・第二判定器。**3 モデルが同じ 13 問に答え、同じ 13 問を外す。**

| モデル | 次元/規模 | answered | direct | paraphrase | 識別力 | MRR |
|---|---|---:|---:|---:|---:|---:|
| `intfloat/multilingual-e5-small`（現行） | 384 / 118M | 13/26 | 11/15 | 2/11 | +30.8pt | 0.436 |
| `cl-nagoya/ruri-v3-30m`（日本語特化） | 256 / 37M | 13/26 | 11/15 | 2/11 | +23.1pt | 0.357 |
| `intfloat/multilingual-e5-base` | 768 / 278M | 13/26 | 11/15 | 2/11 | +26.9pt | 0.412 |

**件数ではなく集合が一致している。**答えた問題名を並べて確認した（同一 13 問:
core-diagnosis, cy-ranking-culture, cy-withdrawal-condition,
gameyard-creatoryard-roles, localization-policy, mkt-deliverables-location,

答えているのを見逃す。

**この測定が潰した仮説**: 「残り 13 問の律速は埋め込みモデルの日本語
言い換え理解である」。設計の違う 3 モデル（多言語小・日本語特化・多言語中）が

候補窓の全域測定（10/20/40/80 も同じ 13）と合わせると、残り 13 問は

`.env.example` の推奨は e5-small のまま据え置き。

**やらないこと**: 別の埋め込みモデルを提案する。3 点測って全滅している。

## それぞれの意味

**到達率** — 実際のコーパスのうち、SIDRA が検索できる割合。
セキュリティゲートを締めると下がる。**安全側の変更が製品側で何を失うかが、
初めて同じ表に載った。** 96.0% は「取り込む範囲の知識の 4% に SIDRA は
触れない」ということ。内訳は sidra-ai 自身の 18.2% が大半で、これは検知器の
ソースコードが検知対象の文字列を含むためで、11:04 に方針として受け入れ済み
（SECURITY.md gap 10）。他 4 本はいずれも 7.1% 以下なので、**到達率の
損失はほぼ全部 SIDRA が自分自身を読めないことに由来する**。

分母は「SIDRA が取り込む範囲」であって「社内の知識全体」ではない。
以前ここには 90.3% と書いてあったが、その分母には製品が取り込まない
アプリのソース 426 文書が入っていた。

**回答可能率** — 実際に運用者が訊きそうな質問のうち、根拠を top-5 に
出せた割合。質問の答えはコーパスに元からあるものだけを使う。

**対照 / 識別力** — ここが重要。この 5 リポジトリは同じ事業の話を
しているので、どんな問い合わせにも「それらしい」文書が返る。無関係な
リポジトリの根拠が紛れ込む割合を対照として同時に測り、その差を識別力と
呼ぶ。**識別力が 0 に近ければ、回答可能率が何%であろうと何も測っていない。**

これは机上の懸念ではない。最初に組んだときの回答可能率は 100% で、
そのときの対照は 16/18 だった。つまり無関係な根拠もほぼ同じ確率で
返っていて、100% という数字には中身が無かった。対照の取り方にも誤りが
あり（隣の質問と対にしたが、隣同士は同じ文書が答えなので対照にならない）、
別リポジトリと対にして測り直して初めて識別力 +33.3pt が出た。
**数字は 3 回作り直して、3 回目でようやく数字になった。**

そして 4 回目が要ることが同じ日のうちに分かった。その +33.3pt も、
答案ファイルが索引に入ったまま測った値だった（上の「取り下げた理由」）。
**「対照を取れ」という教訓を書いた本人が、その対照自身の汚染を見落とした。**
対照は「無関係な根拠が紛れ込むか」を測る仕掛けだが、無関係な根拠と正解の
根拠が同じ 1 ファイルに同居していれば、対照もろとも無意味になる。
測定を疑う仕掛けを足したときは、**その仕掛けが何を前提にしているか**まで
疑うこと。ここでは「マーカーはコーパスの中の別々の文書にある」が前提で、
それが成り立っていなかった。

## いま正直に言えないこと

1. **回答可能率 38.9% は 1 時点の値である。** 同じ入力で 2 回走らせて
   同値になることは確認したが（決定的である）、質問 18 問・1 時点の値である。
   CI では守られていない — 5 リポジトリの checkout が要るので、
   誤検知率のような自動ゲートにはまだなっていない。
   **難しくして下がったら、それは劣化ではなく測定の改善。**
2. **`scripts/measure_gate_baseline.py` の flag% とは一致しない。**
   あちらは commit message と拡張子なしファイルも数えるので、同じ
   sidra-ai が 9.8% と 19.0% になる。母集団が違う数字を比較しないこと。
3. **答えの正しさは測っていない。** 測っているのは「答えを含む文書を
   出せたか」まで。生成された回答が正しいかは別の測定が要る。
4. **18 問はコーパスの一部しか触っていない。** creater-yard と
   marketing の質問はまだ 0 問。この 2 つの到達率は測れているが
   回答可能率は測れていない。合わせて 83 文書が採点対象外である。
5. **`sidra-ai` 自身への質問は 0 問。** 到達率が最も低い（19.0% が索引外）
   リポジトリの回答可能率を測っていない。ここは方針として索引外なので
   低く出るはずで、**測れば「受け入れた損失」が数字になる**。
