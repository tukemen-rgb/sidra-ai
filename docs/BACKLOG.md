# SIDRA AI バックログ

Claude の自動ループが 12 分ごと（毎時 5 回）に参照する作業キュー。
**1 回の起動で 1 件だけ**取る。

選び方は「上から順」ではなく「**`→ 動かす数字:` が付いていて、その数字が
まだ 0 のもののうち最上位**」。0 の数字を持つ項目が 1 件も無いときに限り、
上から順の従来どおりに取る。理由は下の「完了条件」を読むこと。

## 手順 0: 起動したら最初に痕跡を残す（必須）

**他の何よりも先に**、`docs/LOOP_LOG.md` の末尾に 1 行追記して push する。

```
<UTC日時> <トリガー名> started
```

理由: 2026-08-18 の立ち上げで、5 本のループが 3 回発火して**成果が 1 件も
出なかった**。しかし「起動していない」のか「起動したが途中で落ちた」のかを
区別する手段が無く、原因を特定できなかった。この 1 行があれば切り分けられる。

作業を終えたら同じ行の下に結果も 1 行足す（`done <項目名>` / `no-op 理由` /
`failed 理由`）。push が競合したら `git pull --rebase` して再試行する。

**push できない場合はそこで終了し、それ以上進まないこと。** push できない
セッションが作業しても成果は残らない。

## 進め方

各起動は「1 件取り、検証し、main へ入れて閉じる」で完結させる。
枝を作って放置しない。前回の並行開発ではブランチが 326 本まで溜まり、
生産は続いたのに統合が止まった。**閉じないものは進んでいないのと同じ。**

## 完了条件（2026-08-19 変更）

**「commit したか」ではなく「外の数字が動いたか」で判定する。**

commit 数は内部の数字で、増やすだけなら際限なく増やせる。実際そうなった:
A〜D 節を 3 週間かけて閉じ続けた間、**SIDRA に質問するには JSON を手で
組み立てるしかない状態が一度も変わっていない**。テストは 722 本通り、
検知力の回帰もゼロで、それでも製品としては 1 ミリも動いていない。
閉じた項目の数は、動いていないことを隠す方向にしか働かなかった。

外の数字とは、このリポジトリの外にいる人間が気づく数字のこと。
一覧と現在値はこれで出す:

```
python scripts/product_metrics.py --save /tmp/before.json
# ... 1 件やる ...
python scripts/product_metrics.py --compare /tmp/before.json
```

出力は差分ではなく**実際に経路を動かして**測る（ルートは組み立てた app から、
CLI は実際に呼んで、検索スコアは suite を走らせて）。ソースに書いてあるが
端から端まで動かないものは 0 と出る。それが狙い。

### 判定

**`--compare` の終了コードがそのまま判定**なので、目分量で決めない。

| 終了コード | 判定 | すること |
| --- | --- | --- |
| 0 | outcome が動いた（または測れるようになった） | `- [x]`。出力の `LOOP_LOG:` 行を貼る |
| 1 | どの outcome も動かなかった | `- [記録]` か `- [ ]` へ差し戻し |
| 2 | outcome が悪化 / guard を壊した | **マージしない。** revert |


- **`- [x]`** … 上記のどれか 1 つが動いた。行に `(<hash>, <数字> A→B)` を書く。
  作業の前後で `product_metrics.py` を走らせ、両方の値を commit message に残す。
- **`- [記録]`** … 数字は動かないが、決定・却下・調査として残す価値がある。
  **動かないこと自体を 1 行で正当化する。**「テストを足した」「文書を直した」は
  正当化ではない。不変条件を守った・選択肢を潰した、なら正当化になる。
- 数字が動かず正当化もできないなら、その作業は**やらなくてよかった**。
  項目を `- [ ]` に戻して、なぜ空振りだったかを LOOP_LOG に書く。

`- [記録]` が 2 回続いたら、次は必ず 0 のままの数字を持つ項目を取ること。
全部が `- [記録]` で埋まるのは、完了条件を変える前の状態に戻ったということ。

### 注意

数字を動かすこと自体が目的化すると、今度は**測りやすいものだけ触る**という
別の失敗になる。安全側の数字（`documents this repo cannot index`、
`attacks the recall set proves are caught`）を都合よく動かして「進捗」に
しないこと。誤検知率を下げるために検知を削るのは後退であって前進ではない。
そのために `verify_gate_recall.py` と `check_gate_regression.py` が別に在る。

**この懸念は文章での注意喚起から機械的な判定に移した。**出力の数字は
3 階級に分かれていて、`[outcome]` 以外は動いても完了の根拠にならない。

- `[outcome]` — 運用者が気づく能力。**これだけが根拠になる**
- `[guard]` — 守るべき線。守るのは前提であって前進ではない（壊したら 2）
- `[context]` — 実在するが**こちらが書いた量**の数。根拠にならない

`attacks the recall set proves are caught` が `[context]` なのは、検体を
1 件書けば増えるから。同じ理由で `retrieval_cases_*` も `[context]`。
分類の無い数字は `[context]` に落ちる（誰もまだ根拠だと主張していない数字を、
黙って根拠にしないため）。

率にも最小幅がある。`documents this repo cannot index` は 08-19 の午前中に
**10.6% → 10.2% へ下がったが、ゲートは何も良くなっていない**。他のループが
きれいな文書を分母に足しただけだった。0.5 ポイント未満の増減は良い方向でも
悪い方向でも無視する。

## 検証（省略不可）

main へ入れる前に必ず両方を通す。片方でも落ちたら **revert して次へ**。

```
python -m pytest
python scripts/verify_gate_recall.py
python scripts/product_metrics.py      # 作業の前後で走らせ、両方を残す
```

`pytest` ではなく **`python -m pytest`** と書くこと（CI もこちら）。裸の
`pytest` は PATH 上の別インタプリタの実行ファイルを拾うことがあり、その場合
依存が入っていないため collection error だけで落ちる。green の main が赤に
見え、ループが自分の変更を revert する経路になる。

`verify_gate_recall.py` の `MUST CATCH` に 1 つでも `MISS` が出たら、
その変更は検知力を削っている。マージしない。

セキュリティ検知器を触ったときは、実データでの誤検知率も測り直す:

```
python scripts/measure_gate_baseline.py "tukemen-rgb/sidra-ai=<path>" ...
```

現在の基準値は 1012 文書中 **3.5%**（`docs/GATE_FALSE_POSITIVE_BASELINE.md`）。
悪化させた場合は戻す。

      既にメモリ上にある文書は再起動まで残る（ギャップ 9）。検知器を厳しく
      した直後の稼働中プロセスは、古い判定のまま動き続ける。
      → 完了。`DocumentStore.rescreen_all()`。落ちた文書は quarantine へ
      退避する（削除ではなく記録付きの降格）。永続ログは書き換えない
      — あれは「いつ何を通したか」の履歴であり、現在のポリシーに合わせて
      書き換えると**ポリシーが変わった証拠そのものが消える**。
      全件を検査し終えるまで 1 件も退避しないので、検知器が途中で例外を
      投げても索引は元のまま（半分の索引は空より悪い）。

- [x] **独自 CA を設定できない（実機で発見）。**
      `GitHubReadOnlyClient` は httpx の既定 CA しか使わないため、TLS 検査
      プロキシの背後では `CERTIFICATE_VERIFY_FAILED` で全滅する。自社ホスト
      AI が置かれる典型的な企業ネットワークがまさにこれ。
      → 完了。`SIDRA_CA_BUNDLE` で明示指定する。周囲の環境を信頼する形
      （`trust_env=True`）には戻していない — 認証情報をワークステーションの
      プロキシへ漏らさない性質は維持し、**明示的に設定された CA だけ**を使う。
      検証を無効化する選択肢は用意しない（「繋がらないので証明書検査を切った」
      は read-only クライアントが何でも信じ始める入口）。
      証明書エラーが HTTP 応答に変わることで修正を確認した。

- [ ] **実 GitHub API に対する取り込みが一度も検証されていない。**
      取り込み経路のテストはすべて偽トランスポート越しで、本物の API に
      当てたことが無い。差分取得・ページネーション・レート制限・実データの
      形は未検証のまま。上記 CA 修正の確認中に判明した。
      なお開発環境からは直接 API を叩けない（プロキシが 403 を返す）ので、
      **社長の手元か、外に出られる環境で確認する必要がある**。
      手順: `SIDRA_CA_BUNDLE` を必要なら設定し、`sidra-api` を起動して
      `POST /v1/github/analyze` を 2 回叩く。2 回目が `inference_skipped: true`
      になれば差分取得が実際に効いている。

### E. 判断が要る（実装せず、社長の判断を待つ）

- [ ] **要判断: BLOCK の監査記録がリポジトリを残さない。**上の調査で判明。
      取り込みレポートは「site で 2 件、byte_budget」と言えるが、これは
      `POST /v1/github/analyze` の応答であって永続しない。永続する側
      （quarantine 監査ログ）は BLOCK について `source` / `repository` を
      落とし、長さだけを残す。BLOCK は secret/PII 検査より前に起き得るため
      という理由（ギャップ 6）は**許可リスト拒否の BLOCK では正しい**が、
      サイズ超過の BLOCK では `repository` は既に許可リストを通過している。
      QUARANTINE が同じ理由で `source` / `repository` を残しているのと
      同じ条件が揃っている。
      **それでも実装しない。**現在の挙動は
      `tests/test_quarantine_provenance_privacy.py` と
      `src/sidra_ai/evals/quarantine_provenance_privacy.py` の両方が意図的に
      固定しており、privacy の保護範囲を狭める変更である。誰かが意図して
      書いた保護を、ループが黙って反転させる類の変更ではない。
      直すなら「UNPERMITTED_SOURCE の finding を持たない BLOCK のみ
      source/repository を残す」で、テストと eval の該当アサーションを
      同時に更新する。

### G. 製品を実際に使えるものにする（2026-08-19 追加）

現状の SIDRA は「5 リポジトリを読んで引用付きで答える」ところまで来たが、
**運用に載せるには足りない**。以下は使えるようにするための具体作業。

- [x] → 動かす数字: `ingestion_automatic` **0→1** (4bd51b2)
      **取り込みが手動でしか走らない。**誰かが `POST /v1/github/analyze` を
      叩かないと知識が古びる。自社ホスト AI が「最後に叩いた時点の記憶」で
      答えるのは事故のもと。バックグラウンドで定期的に差分取り込みを回す
      仕組みを入れる。差分が無ければモデルを呼ばない性質は既にあるので、
      頻度を上げてもコストは増えない。**設定で無効化できること**、
      停止中でも API は動くこと。
      → 完了。`SIDRA_INGEST_INTERVAL_SECONDS`（既定 0 = 無効、有効なら 60 秒以上）。
      `BackgroundRefresher` が専用スレッドで回す（ingestion は blocking なので
      event loop に載せると全リクエストが止まる）。
      **モデルへの経路を持たない**: エンドポイントは差分があれば要約するが、
      定期実行は `ingest_only()` だけを呼ぶ。「変化が無ければ呼ばない」より
      「そもそも呼べない」の方が強く、将来エンドポイント側のコスト判定を
      触っても壊れない。
      失敗は記録して継続（API が落ちるのは陳腐な答えより悪い）。
      status は repository 名も例外文も持たない（型だけ残す）。
      初回 tick は interval 待ってから（再起動ループが fetch 洪水になるため）。
      `/health` には出さない — 未認証で topology を出さない不変条件を維持。
- [x] **何が索引に入っているか外から見えない。**`GET /v1/index` を作った。
      リポジトリ別・source_type 別の件数、最終取り込み時刻・commit、隔離件数。
      **本文は返さない**（引用は `/v1/retrieve` の仕事）。認証必須。
      → **許可リストの全リポジトリを、0 件でも必ず行として返す。**
      行が無いのは「取り込んでいない」ではなく「何も言っていない」であり、
      薄い答えの原因を切り分けるというこの endpoint の目的そのものが果たせない。
      `last_error` は**真偽値にした**。中身は例外文字列 500 文字までで
      GitHub の応答を引用し得るため、報告面が例外テキストの経路になる。
      quarantine ログが読めないときは 0 ではなく `available: false` を返す。
      0 は「何も止まっていない」と読め、読めない監査ログの意味と正反対になる。
      `/health` は従来どおり件数もリポジトリ名も返さない（未認証のため）。
      `test_no_write_routes_exist` の経路一覧は意図的な厳密一致なので、
      read-only 経路の追加として明示的に更新した。
      (1b1f166, index_visible 0→1)
- [x] → 動かす数字: `ask_without_json` **0→1**
      **`sidra ask "質問"` の CLI。**curl で JSON を組み立てないと質問
      できないのは、日常的に使う道具として障害が大きすぎる。
      `/v1/chat` を叩いて答えと引用を読みやすく表示するだけでよい。
      API が起動していなければその旨を出す。
      → 完了。`sidra-ask "質問"`（`src/sidra_ai/api/ask_cli.py`）。
      API に無い機能は足していない。終了コードで区別する:
      0 回答 / 1 到達不能・API エラー / 2 設定拒否 / 3 ゲートが拒否。
      「拒否された」と「API が落ちている」は正反対の問題なので、
      呼び出し側が区別できないと調べる場所を間違える。
      **トークンは設定した宛先にしか送らない。**`--url` は別ポートに
      届くための便宜だが、コマンドラインに書いた任意のホストへ bearer
      トークンを渡す経路でもある。設定ホストと loopback 以外は
      黙って認証を外すのではなく拒否する（黙って外すと 401 になり、
      「トークンが違う」に見えて原因から遠ざかる）。
      **表示するものは実行しない。**出力はすべてリポジトリ由来の DATA で、
      端末は制御列を解釈する。エスケープ列は自分を暴くはずの引用行を
      消せるし、bidi override はリポジトリ名を別の名前に見せられる。
      表示前に除去し、**除去したこと自体を stderr に出す**（黙って
      書き換えない）。`--json` は素の値を出すが、JSON が制御文字を
      テキストとして符号化するので端末には安全。(8c7eacb)
- [x] → 動かす数字: `conversation_turns` **1→2** (3c2e011)
      **会話が 1 往復で終わる。**`/v1/chat` は毎回独立で、前の質問を
      覚えていない。追加質問ができないと調査用途で使えない。
      直前のやり取りを渡せるようにする。**ただし過去の回答を新たな
      instruction にしない**こと（DATA と同じ扱いで envelope に入れる）。
      → 完了。`ChatRequest.history`（最大 8 往復・各 8000 字）。
      **trust は `UNVERIFIED`。**ここがこの変更の全てで、`OPERATOR` に
      しなかったのは `OPERATOR` が instruction authority だから
      （`DATA_ONLY_TRUST_LEVELS` に入っていない）。API は状態を持たないので
      履歴は**クライアントの主張**であって記録ではなく、「SIDRA は以前
      こう言った」と書けば誰でも instruction を作れることになる。
      主張は DATA である、という 1 行に落とした。
      履歴は現在のメッセージと同じゲートを通す（運用者は追加質問にも秘密を
      貼れるし、クライアントは何でも入れられる）。1 往復を 2 ブロックに
      分けるのは、片側に紛れ込んだ `sidra:` 行がもう片側を飲み込まないため。
      `system_prompt` / `user_message` には決して入らない。
      検索は現在の質問だけで引き、**0 件のときだけ**直前の質問を足して
      1 回だけ引き直す（「それはなぜ？」は単独では引けない）。ヒットした
      クエリは書き換えないので、単発検索の品質は動かない。
      監査記録は履歴の文字数を `input_chars` に足すが本文は残さない。
      既知の限界: 引き直しは直前の質問がコーパスと同じ言語のときだけ効く。
      日本語の追加質問と英語の文書は bigram と語トークンで噛み合わない。
      これは会話機能ではなくトークナイザの性質で、別項目。
- [x] **外部 API 0 円が測定されていない。**これはプロジェクトの目的そのもの
      なのに、トークン消費もコストも記録していない。`external_api_cost_usd`
      を返してはいるが常に 0.0 の定数で、**証明ではなく主張**。
      → 完了。`models/usage.py` の `UsageLedger` + `MeteredAdapter`。
      **0 円は既に構造で保証されている**（registry が有料 backend を登録拒否）。
      台帳が足すのは保証ではなく**観測可能性**で、誰にも見えない保証は
      仮定と区別がつかない。`external_api_cost_usd` は各呼び出しの報告値の
      合計になり、0 以外が来たら記録時点で例外を投げる。
      アダプタを包む方式にしたので、将来の backend は「呼び出しを足し忘れる」
      余地なく計測される。台帳は本文を一切保持しない
      （会計記録が秘密の置き場になっては本末転倒）。
      トークン数・所要時間・トークン毎秒も記録するので、32B が実用速度かの
      判断材料になる。エンドポイント公開は「何が索引に入っているか」の項目と
      一緒にやる。
