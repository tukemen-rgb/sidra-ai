# SIDRA AI バックログ

Claude の自動ループが 12 分ごと（毎時 5 回）に参照する作業キュー。
**1 回の起動で 1 件だけ**取る。

選び方は「上から順」ではなく「**`→ 動かす数字:` が付いていて、その数字が
まだ 0 のもののうち最上位**」。0 の数字を持つ項目が 1 件も無いときに限り、
上から順の従来どおりに取る。理由は下の「完了条件」を読むこと。

## 手順 0: 起動したら最初に痕跡を残す（必須）

**他の何よりも先に**、`docs/LOOP_LOG.md` の末尾に 1 行追記して push する。

```
<UTC日時> <トリガー名> started
```

理由: 2026-08-18 の立ち上げで、5 本のループが 3 回発火して**成果が 1 件も
出なかった**。しかし「起動していない」のか「起動したが途中で落ちた」のかを
区別する手段が無く、原因を特定できなかった。この 1 行があれば切り分けられる。

作業を終えたら同じ行の下に結果も 1 行足す（`done <項目名>` / `no-op 理由` /
`failed 理由`）。push が競合したら `git pull --rebase` して再試行する。

**push できない場合はそこで終了し、それ以上進まないこと。** push できない
セッションが作業しても成果は残らない。

## GDP 連携（AI Review Board = Issue #372）

各ループは**手順1（痕跡）の直後**に Issue #372 のコメント総数を確認する
（`mcp__github__issue_read` method:get で総数だけ。LOOP_LOG の直近の
`Board=NN` と比べ、増えたときだけ新コメントを読む。読んだら started 行に
`Board=NN` を添える）。**訂正 2026-08-20 ループB: 総数には自分の返信も入る。**
実測: Board=3 を仕分けて 2 件返信したら次の回は Board=5 になり、増分 2 件は
**全部こちらの投稿**だった。返信するたびに次のループが「新着 2 件」を見る。
しかも投稿者は全員 owner なので**著者では切り分けられない**。増分を読んだら
**帰属フッター `_Generated by [Claude Code]` が付いているものは自分の投稿**
として捨てること（総数だけを信じて動かない）。GitHub ツールが使えない回は確認をスキップしてよい
（次の回が拾う）。新コメントの扱い:

- **数字つきの提案** → この BACKLOG に `→ 動かす数字:` つきで起票し、
  起票した旨を #372 に返信（帰属フッター付き）。実装はキューの順番どおり。
- **判断が要る提案**（不変条件・E 節領域）→ E 節に記録し「社長へ」と返信。
- **事実誤認** → 実測値と出典（OUTCOMES.md 等）を添えて訂正を返信。
- 返信は必要なときだけ。相槌や重複報告を投稿しない。

GDP の提案も**完了条件は同じ**（判定器の終了コードで判定）。提案元が
誰であっても、数字が動かない変更は `[記録]` 以上にならない。

## 進め方

各起動は「1 件取り、検証し、main へ入れて閉じる」で完結させる。
枝を作って放置しない。前回の並行開発ではブランチが 326 本まで溜まり、

## 完了条件（2026-08-19 変更）

**「commit したか」ではなく「外の数字が動いたか」で判定する。**

commit 数は内部の数字で、増やすだけなら際限なく増やせる。実際そうなった:
A〜D 節を 3 週間かけて閉じ続けた間、**SIDRA に質問するには JSON を手で
組み立てるしかない状態が一度も変わっていない**。テストは 722 本通り、
検知力の回帰もゼロで、それでも製品としては 1 ミリも動いていない。
閉じた項目の数は、動いていないことを隠す方向にしか働かなかった。

外の数字とは、このリポジトリの外にいる人間が気づく数字のこと。
一覧と現在値はこれで出す:

```
python scripts/product_metrics.py --save /tmp/before.json
# ... 1 件やる ...
python scripts/product_metrics.py --compare /tmp/before.json
```

出力は差分ではなく**実際に経路を動かして**測る（ルートは組み立てた app から、
CLI は実際に呼んで、検索スコアは suite を走らせて）。ソースに書いてあるが
端から端まで動かないものは 0 と出る。それが狙い。

### 判定

**`--compare` の終了コードがそのまま判定**なので、目分量で決めない。

**例外が 1 つある。**項目の `→ 動かす数字:` が `answerable_*` のときは、
判定器は `product_metrics.py` ではなく **`check_answerable_regression.py` の
`--save` / `--compare`** を使う（意味論は同一: 0=動いた / 1=動かない / 2=悪化）。
理由: `product_metrics.py` は設計としてオフライン数秒で走る計器なので、
5 checkout の要る回答可能率は載せられない。載っていない数字は `--compare` で
動けないため、こちらの判定器を使う。手順:

```
python scripts/check_answerable_regression.py <5つの repo=path> --save /tmp/ans-before.json
# ... 実装 ...
python scripts/check_answerable_regression.py <5つの repo=path> --compare /tmp/ans-before.json
```

出力の `corpus moved` 警告が出たら、動いた数字は他人の push 由来かもしれない。
--save を取り直して確かめてから完了にすること。

| 終了コード | 判定 | すること |
| --- | --- | --- |
| 0 | outcome が動いた（または測れるようになった） | `- [x]`。出力の `LOOP_LOG:` 行を貼る |
| 1 | どの outcome も動かなかった | `- [記録]` か `- [ ]` へ差し戻し |
| 2 | outcome が悪化 / guard を壊した | **マージしない。** revert |


- **`- [x]`** … 上記のどれか 1 つが動いた。行に `(<hash>, <数字> A→B)` を書く。
  作業の前後で `product_metrics.py` を走らせ、両方の値を commit message に残す。
- **`- [記録]`** … 数字は動かないが、決定・却下・調査として残す価値がある。
  **動かないこと自体を 1 行で正当化する。**「テストを足した」「文書を直した」は
  正当化ではない。不変条件を守った・選択肢を潰した、なら正当化になる。
- 数字が動かず正当化もできないなら、その作業は**やらなくてよかった**。
  項目を `- [ ]` に戻して、なぜ空振りだったかを LOOP_LOG に書く。

`- [記録]` が 2 回続いたら、次は必ず 0 のままの数字を持つ項目を取ること。
全部が `- [記録]` で埋まるのは、完了条件を変える前の状態に戻ったということ。

### 注意

数字を動かすこと自体が目的化すると、今度は**測りやすいものだけ触る**という
別の失敗になる。安全側の数字（`documents this repo cannot index`、
`attacks the recall set proves are caught`）を都合よく動かして「進捗」に
しないこと。誤検知率を下げるために検知を削るのは後退であって前進ではない。
そのために `verify_gate_recall.py` と `check_gate_regression.py` が別に在る。

**この懸念は文章での注意喚起から機械的な判定に移した。**出力の数字は
3 階級に分かれていて、`[outcome]` 以外は動いても完了の根拠にならない。

- `[outcome]` — 運用者が気づく能力。**これだけが根拠になる**
- `[guard]` — 守るべき線。守るのは前提であって前進ではない（壊したら 2）
- `[context]` — 実在するが**こちらが書いた量**の数。根拠にならない

`attacks the recall set proves are caught` が `[context]` なのは、検体を
1 件書けば増えるから。同じ理由で `retrieval_cases_*` も `[context]`。
分類の無い数字は `[context]` に落ちる（誰もまだ根拠だと主張していない数字を、
黙って根拠にしないため）。

率にも最小幅がある。`documents this repo cannot index` は 08-19 の午前中に
**10.6% → 10.2% へ下がったが、ゲートは何も良くなっていない**。他のループが
きれいな文書を分母に足しただけだった。0.5 ポイント未満の増減は良い方向でも
悪い方向でも無視する。

## 検証（省略不可）

main へ入れる前に必ず両方を通す。片方でも落ちたら **revert して次へ**。

```
python -m pytest
python scripts/verify_gate_recall.py
python scripts/product_metrics.py      # 作業の前後で走らせ、両方を残す
```

`pytest` ではなく **`python -m pytest`** と書くこと（CI もこちら）。裸の
`pytest` は PATH 上の別インタプリタの実行ファイルを拾うことがあり、その場合
依存が入っていないため collection error だけで落ちる。green の main が赤に
見え、ループが自分の変更を revert する経路になる。

`verify_gate_recall.py` の `MUST CATCH` に 1 つでも `MISS` が出たら、
その変更は検知力を削っている。マージしない。

セキュリティ検知器を触ったときは、実データでの誤検知率も測り直す:

```
python scripts/measure_gate_baseline.py "tukemen-rgb/sidra-ai=<path>" ...
```

現在の基準値は 1012 文書中 **3.5%**（`docs/GATE_FALSE_POSITIVE_BASELINE.md`）。
悪化させた場合は戻す。

      叩かないと知識が古びる。自社ホスト AI が「最後に叩いた時点の記憶」で
