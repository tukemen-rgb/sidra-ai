# SIDRA AI バックログ

Claude の自動ループが 12 分ごと（毎時 5 回）に参照する作業キュー。
上から順に、**1 回の起動で 1 件だけ**取る。

## 手順 0: 起動したら最初に痕跡を残す（必須）

**他の何よりも先に**、`docs/LOOP_LOG.md` の末尾に 1 行追記して push する。

```
<UTC日時> <トリガー名> started
```

理由: 2026-08-18 の立ち上げで、5 本のループが 3 回発火して**成果が 1 件も
出なかった**。しかし「起動していない」のか「起動したが途中で落ちた」のかを
区別する手段が無く、原因を特定できなかった。この 1 行があれば切り分けられる。

作業を終えたら同じ行の下に結果も 1 行足す（`done <項目名>` / `no-op 理由` /
`failed 理由`）。push が競合したら `git pull --rebase` して再試行する。

**push できない場合はそこで終了し、それ以上進まないこと。** push できない
セッションが作業しても成果は残らない。

## 進め方

各起動は「1 件取り、検証し、main へ入れて閉じる」で完結させる。
枝を作って放置しない。前回の並行開発ではブランチが 326 本まで溜まり、
生産は続いたのに統合が止まった。**閉じないものは進んでいないのと同じ。**

完了した項目は `- [x]` にして、その行に commit hash を書く。

## 検証（省略不可）

main へ入れる前に必ず両方を通す。片方でも落ちたら **revert して次へ**。

```
pytest
python scripts/verify_gate_recall.py
```

`verify_gate_recall.py` の `MUST CATCH` に 1 つでも `MISS` が出たら、
その変更は検知力を削っている。マージしない。

セキュリティ検知器を触ったときは、実データでの誤検知率も測り直す:

```
python scripts/measure_gate_baseline.py "tukemen-rgb/sidra-ai=<path>" ...
```

現在の基準値は 1012 文書中 **3.5%**（`docs/GATE_FALSE_POSITIVE_BASELINE.md`）。
悪化させた場合は戻す。

- [x] **`high_entropy` の発火 1018 回を減らす。**ほぼ全文書で 1 回以上鳴る。

- [!] **却下: RFC 2606 予約ドメイン（`example.com`）の誤検知。**
      UI プレースホルダ `placeholder="mail@example.com"` が個人メール扱いで
      site の 4 文書が隔離される。予約ドメインは実在し得ないので、製品の
      挙動としては確かに誤検知である。**それでも直さない。**
      予約ドメインを PII 対象外にすると、リポジトリ内の 12 箇所の PII 検体
      （`synthetic_pii`、`private.person@example.com` 等・6 ファイル、
      `src/sidra_ai/evals/quarantine_provenance_privacy.py` を含む）が
      「検知されない値」に変わり、監査記録・quarantine provenance・出力の
      各 PII 漏洩テストが**何も検証しなくなる**。
      さらに本質的な問題として、**予約ドメインは「実在しない PII 検体」を
      安全に書ける唯一の手段**である。これを対象外にすると、今後 PII の
      テストを書くとき実在しうるドメインを使うしかなくなり、リポジトリに
      本物の個人情報を書き込む圧力が生まれる。
      得られるのは UI コンポーネント 4 件の索引化のみ。**割に合わない。**
      再検討するなら、ドメインではなく「`placeholder` 属性の値である」と
      いう文脈で判定する方向。ただし正規表現ベースの検知器には荷が重い。
- [ ] **SIDRA が自分自身のセキュリティ実装を検索できない。**攻撃パターンを
      記述したコードとテストが隔離される（sidra-ai 単体で 6.3%）。挙動として
      正しいとも言えるが、運用上は自分の実装を引けない。方針を決めて記録する。
- [ ] 巨大 JSON（`site` の 2 件）がサイズ上限で BLOCK。データ配列であり文書では
      ないので妥当だが、検索対象にしたいなら別経路が要る。

### B. 運用に必要な穴

- [x] **quarantine の release ワークフロー。**隔離された文書が溜まる一方で、
      → 完了。`sidra-quarantine list / show / release / stats`。
      解放は「人が理由付きで承認した記録を残す」だけで、自動再索引はしない。
      QUARANTINE のみ解放可（BLOCK は方針上の拒否であり再判断の対象外）。
      操作者名と 8 文字以上の理由が必須。値は既定で表示しない。
- [x] **索引の永続化。**プロセス再起動で消える。sqlite + FTS5 を想定。
      → 完了。`DocumentStore.load()` で JSONL から復元する。sqlite/FTS5 は
      まだだが、再起動で消える問題自体は解消した（再取得が不要になる）。
      **読み込み時に必ず再検査する。**索引は過去の判定のキャッシュであって
      恒久的な許可ではなく、検知器を厳しくした後に無検査で復元すると
      その修正を黙って巻き戻すため。落ちた記録は件数と理由を報告し、
      修復はしない（黙って書き換えるより落とすほうが見える）。
      破損した末尾行は 1 件の損失で済み、全体を読み終わるまで索引は変更しない。
- [x] `docs/SECURITY.md` の「既知のギャップ」を現状に合わせて更新。
      → 完了。解消済み（quarantine release）を実態に書き換え、新たに 3 件を
      追加（索引はポリシー変更時に再起動が要る / 自分自身のセキュリティ実装を
      検索できない / 誤検知率は測定しているだけで強制されていない）。
      「主張を自分で検証する方法」の節も追加した。

## 厳守事項

1. **1 回の起動で 1 テーマ、目安 400 行以内。**超えるなら分割し、残りをここへ書く。
2. 赤いまま main へ入れない。落ちたら直すか revert する。
3. API key / token / password / 個人情報 を、コード・commit・ログ・テストへ書かない。
   認証情報の形をしたテスト値は**必ず反復で生成**する（例: `"ghp_" + "0" * 36`）。
   直書きは規約違反（`tests/test_fetch_policy.py:33` に前例あり）。
4. 外部 LLM API を使わない。有料 API を依存に追加しない。
5. GitHub への書き込み機能を製品に実装しない（v0.1 は read-only）。
6. 本番 deploy をしない。GAMEYARD / CreatorYard 本体を変更しない。
7. キューが空なら**何もせずに終える**。埋めるための作業を作らない。

### D. 次の一手（2026-08-18 追加。根拠は docs/SECURITY.md の既知ギャップ）

- [x] **誤検知率を CI ゲートにする。**現在 3.5% という数字は測っているだけで、
      **倍にする変更も CI を通る**（SECURITY.md ギャップ 11）。習慣であって
      ゲートではない。`scripts/measure_gate_baseline.py` を CI で走らせ、
      基準値からの悪化で落とす。基準値はファイルに固定し、意図的な変更は
      その更新を伴わせる。合成コーパスで測るか実リポジトリを clone するかは
      → 完了。`scripts/check_gate_regression.py` が CI で走る。CI から他
      リポジトリは読めないので、**チェックアウト済みの自リポジトリ**を測る。
      上限は 13%（実測 10.1%）。厳密一致ではなく上限にしたのは、ファイルを
      1 つ足すたびに落ちると「読まずに数字を上げる」習慣がつき、この検査が
      防ごうとしている失敗そのものになるため。上限を上げるのは可だが、
      このファイルの意図的な編集と commit message での理由が要る。
- [x] **`verify_gate_recall.py` を CI に入れる。**検知力の回帰を防ぐ唯一の
      機械的手段なのに、人が思い出したときにしか走らない。8 桁国際番号の
      → 完了。push / PR で必ず走る。テストでも「CI に入っていること」自体を
      検査している（パイプラインから外れた検査は制御ではないため）。
- [x] **解放された quarantine を索引へ戻す経路。**`sidra-quarantine release`
      は承認を記録するが、**それを読んで再索引する側が無い**。承認しても
      何も起きないので、ワークフローが半分しか閉じていない。
      `released_entries()` を使い、ingestion 側に取り込み口を作る。
      → 完了。ただし**設計上の壁があった**: privacy 強化により quarantine の
      記録から path / commit_sha / license が消えており、記録だけからは
      Document を再構成できなかった。値を晒さずに解決するため、記録に
      `document_id`（repository+path+commit+content のハッシュ）だけを追加した。
      これは中身を明かさず、次回取り込み時に再計算できるので、解放を
      「その文書に対する承認」として適用できる。
      `SecurityGate(released_document_ids=...)` が QUARANTINE のみ参照する。
      BLOCK は方針上の拒否なので承認しても通さない。承認元が壊れていたら
      fail closed（何も通さない）。findings は記録に残したまま通す
      （承認は「見た上で受け入れた」であって「何も無かった」ではない）。
- [~] 作業中 2026-08-18 15:48 UTC — **稼働中の索引をポリシー変更時に再検査する。**`load()` は再検査するが、
      既にメモリ上にある文書は再起動まで残る（ギャップ 9）。検知器を厳しく
      した直後の稼働中プロセスは、古い判定のまま動き続ける。
      `DocumentStore.rescreen_all()` を作り、再検査で落ちた文書を退避する。

### E. 判断が要る（実装せず、社長の判断を待つ）
