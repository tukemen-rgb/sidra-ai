## 1. Juice（手触り）— 動きと音が無いゲームは死んでいる

- 出典: https://abagames.github.io/joys-of-small-game-development-en/make_game_juicy.html（2026-08-29 確認）
- 事実: 小規模ゲーム向けの juice 技法として、色数の工夫・トゥイーン/イージング・
  イベントに応じた拡縮バウンス・効果音と音楽・多数パーティクル（煙/破壊/軌跡）・
  画面揺れ・キャラの目や表情・**被弾時のヒットストップとノックバック**を列挙。
  開発時間が限られるときはパーティクルと音だけでも効果的、と明記。
- 事実: 元ネタは Jonasson & Purho の講演「Juice it or lose it」（Nordic Game Jam
  2012）。凡庸なブロック崩しに演出を足すだけで生き返る実演。Vlambeer の
  「The Art of Screenshake」は揺れの原則として「爆発や重い一撃でカメラを数 px
  蹴り、素早く減衰。イベントの重さに揺れを比例させる」。
  （出典: https://www.gamedeveloper.com/design/squeezing-more-juice-out-of-your-game-design- 2026-08-29 確認）
- 学び: SIDRA の 4 テンプレには音が 1 つも無く、揺れ・ヒットストップも無い。
  **最小の投資で最大の体感差が出るのは音 → 揺れ/ヒットストップ → パーティクル の順。**
- SIDRA での反映先: C-1017（効果音）/ C-1020（揺れ・ヒットストップ・粒子）**→ 反映済み 2026-08-29（C-1020 完了: 重さ比例の画面揺れ・被弾/撃破のヒットストップ・草刈り/宝石/命中の粒子を 4 テンプレ全部に配線。reduced-motion で揺れと粒子は 0、ヒットストップは残す）**

## 2. 効果音はブラウザ内で合成できる（外部ファイル不要）

- 出典: https://sfxr.me/ ・ https://github.com/chr15m/jsfxr（2026-08-29 確認）
- 事実: sfxr（DrPetter 作）系のレトロ効果音は、波形種別＋ADSR エンベロープ
  （attack/sustain/punch/decay）＋周波数（基準/傾き）＋ビブラート＋デューティ比＋
  ローパス/ハイパスの少数パラメータで合成される。定番プリセット名は
  pickupCoin / laserShoot / explosion / powerUp / hitHurt / jump / blipSelect。
  jsfxr はこれを Web Audio API で再生する JS ライブラリ。
- 学び: プリセットの正体は「オシレータ＋短いエンベロープ」なので、**ライブラリを
  入れなくても Web Audio の OscillatorNode + GainNode で同等の 8bit 風 SFX を
  数十行で自作できる**（SIDRA の自己完結・外部取得なしの原則と両立）。
  ブラウザの自動再生制限があるため、AudioContext は最初のユーザー操作で resume する。
- SIDRA での反映先: C-1017（creation/audio.py として自作合成。jsfxr のコードは
  移植しない＝パラメータ設計の考え方のみ参考）**→ 反映済み 2026-08-29（C-1017 完了、12 種の SFX を 4 テンプレに配線）**
- 事実（増築 2026-09-08・辛口クリエイターループ。URL は同日に実際に開いて
  確認）: **StereoPannerNode は音を左右のステレオ像に置く 1 ノード**——
  「a simple stereo panner node that can be used to pan an audio stream
  left or right」。pan は a-rate AudioParam で **-1=左端・0=中央・+1=右端**、
  equal-power の低コスト実装で、PannerNode のはるかに簡易な代替として
  導入された。Baseline: Widely available（2021-04 以来全主要ブラウザ）。
  （出典: https://developer.mozilla.org/en-US/docs/Web/API/StereoPannerNode）
- 学び: SIDRA の 12 音は全部**中央**で鳴る。画面には左右が常にある——
  shooter の撃墜は f.x で・kaiju の脚は legX() で起きる——のに、耳は
  どこで起きたかを教わらない。§2 の合成品質・§14 の反復変化・§21 の
  譲り合いまで来て、**定位だけが無い**。sfx に正規化 x（0..1）の第 3
  引数を足し、±0.8 に絞って（端に張り付けない）出来事の位置を耳へ。
- SIDRA での反映先: C-1394（sfx の定位——shooter 撃墜と kaiju 脚打の
  2 サイトから・判定器 creation_sfx_pan）

## 3. ロック＆キー構造（ゼルダ型の骨格）

- 出典: https://www.boristhebrave.com/2021/02/27/lock-and-key-dungeons/（2026-08-29 確認）
- 事実: ロックは進行を止めるもの、キーはそれを解くもの。種類は物理アイテムに
  限らず、道具（爆弾/矢）・能力アップグレード・知識（パスワード）・イベントフラグ。
  hard（正規手段でしか開かない）と soft（上手い人は迂回できる）の区別がある。
  依存関係は mission graph（A を開けないと B に行けない）で表せる。
  一本道でなく**複数の経路と任意の探索報酬**があるときに面白くなる。
- 事実: 現代ゼルダの単純化形は「並列の 4〜5 部屋を解く→ボス鍵→ボス」。
  Mark Brown（GMTK）の Boss Keys 図法は小鍵/扉/ボス鍵を記号化して物理配置と
  論理進行を同時に描く。（出典: https://www.patreon.com/posts/how-my-boss-key-13801754 ほか 2026-08-29 確認）
- 学び: SIDRA の adventure は「鍵 1 個の完全一本道」= mission graph が線 1 本。
  **面白さの最低条件は「分岐 1 つ＋任意報酬 1 つ」から。**部屋テンプレを増やす
  よりも、同じ 3 部屋の中に「開けなくてもよい扉」を足す方が効く。
- SIDRA での反映先: C-1021（分岐と任意報酬）/ 将来の部屋数拡張**→ 反映済み 2026-08-29（C-1021 完了: 洞窟に「開けなくてもよい扉」1 つ＋その奥に護符。扉以外に入口が無いことを実際に世界を build して確認）**

## 4. 視認性・アクセシビリティ（読める画面の最低条件）

- 出典: https://gameaccessibilityguidelines.com/basic/（2026-08-29 確認）
- 事実: 基本ガイドラインとして「テキスト/UI と背景に高いコントラスト」
  「**固定の色だけで本質情報を伝えない**（形・パターン・文字を併用）」
  「タッチ画面では操作要素を大きく・間隔を空けて」「操作の再割り当てを許す」
  「明滅と反復パターンを避ける」。
- 事実: モバイルのタッチ目標は最低 48x48dp・間隔 8dp が業界標準。
  （出典: https://www.gamedeveloper.com/game-platforms/accessibility-heuristics-and-evaluation-criteria-for-mobile-games 2026-08-29 確認）
- 学び: adventure の壁と床は同系色で「色だけ」の区別＝ガイドライン違反そのもの。
  壁には輪郭と明度差、ドアには形のある標識が要る。スマホの移動手段が無いのは
  タッチ操作ガイドライン以前の欠落。
- 事実（増築 2026-09-04・辛口クリエイターループ。URL は同日に実際に開いて
  確認）: 「高いコントラスト」の定量は **WCAG 1.4.3**——通常サイズの
  テキストは背景に対し **4.5:1 以上**、大きなテキスト（18pt≒24px、太字
  14pt≒18.5px 以上）は **3:1 以上**。非テキスト UI 部品は関連基準
  1.4.11 が扱う。動く背景の上の HUD は「最も不利な場面」で測ること——
  §7 の最終幕最明の空はまさにその場面で、暗い空を前提に決めた HUD の
  文字色は最明の幕でだけ静かに沈む。
  （出典: https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html）
- SIDRA での反映先: C-1329（時計 3 型の HUD——空が明るくなった分だけ
  文字が沈む／puzzle は光テーマで HUD が消えている）
- 事実（増築 2026-09-07・辛口クリエイターループ。URL は同日に実際に開いて
  確認）: **WCAG 1.4.11 Non-text Contrast——UI 部品と図的オブジェクトの
  視覚提示は隣接色に対し 3:1 以上**。対象は部品の同定に必要な視覚情報
  （存在・操作方法・状態）で、テキストや図像など他の十分な視覚手がかりが
  あれば境界そのものは免除だが、**境界が唯一の識別子ならその境界が 3:1 を
  満たす**こと。「隣接色」は部品の外側の色（白地の入力欄なら外側の白）。
  無効化された部品と純装飾は免除。
  （出典: https://www.w3.org/WAI/WCAG21/Understanding/non-text-contrast.html）
- 学び: 仮想パッド（C-1019・スマホ唯一の操作手段）は raised の板 α0.72＋
  border の縁 2px を**そのとき描かれている場面の床の上に**合成するが、
  実測 12 セル（catch×4 テーマ×3 場面）中 9 で板・縁の最良でも 3:1 未達
  （最悪 1.05:1=紙テーマでほぼ不可視）。グリフも border 色で板に対し約
  1.2:1。場面の床は幕ごとに明度が動く（§7 観察 6 の明度予約）ので単色の
  縁では常時 3:1 を張れない——**ink と surface の両極 2 重リング（α1.0）
  なら「どちらかが必ず 3:1」が全セルで成立**（実測最悪 4.79:1）。
- SIDRA での反映先: C-1388（パッドの 2 重リングとグリフの ink 化・
  判定器 creation_pad_visible）
- 事実（増築 2026-09-07・辛口クリエイターループ。URL は同日に実際に開いて
  確認）: GAG 中級に**「Provide an option to turn off / hide background
  movement」**——背景の動きを切るオプションの提供——が Cognitive と
  Vision の**両カテゴリに同文で**載っている（動きが認知負荷と視覚の
  両方に効くという整理）。
  （出典: https://gameaccessibilityguidelines.com/full-list/）
- 学び: SIDRA の REDUCED は OS の prefers-reduced-motion **のみ**を読む。
  OS 設定に手が届かない人（借り物の端末・学校の PC・設定の場所を知らない
  人）には動きを減らす手段がゼロ——調整パネルは音量・振動という「部屋に
  要らないチャンネル」を既に持つのに、第 3 のチャンネル＝動きだけが無い。
  OS 設定は約束なので **パネルは足す方向にだけ効く**（OS が reduce なら
  パネルで戻せない・OR 結合）が正しい。
- SIDRA での反映先: C-1393（調整パネルの「動きを減らす」スイッチ・
  判定器 creation_motion_switch）
- 事実（増築 2026-09-08・辛口クリエイターループ。URL は同日に実際に開いて
  確認）: Netflix の日本語 Timed Text Style Guide は**読速を「Up to 4
  characters per second」**（通常字幕・I.19）、SDH でも 7 文字/秒（II.18）、
  **最短表示 500ms**（I.9）と定める。読める速さには業界の数値がある。
  （出典: https://partnerhelp.netflixstudios.com/hc/en-us/articles/215767517-Japanese-Timed-Text-Style-Guide）
- 学び: adventure/platformer の say() は**文字数を知らない一律 140/150
  フレーム**（2.3〜2.5 秒）。「鍵がかかっている。洞窟の敵が持っている
  らしい。」（22 文字）は 9.4 文字/秒——通常字幕の 2.4 倍・SDH 基準すら
  超えて消える。進行に必要な情報（鍵の場所・祠の値段・石碑の順）が
  読み切れない速さで流れるのは §4「読める画面」の時間軸版の欠け。
  表示時間は文字数から: 15 フレーム/文字（=4 文字/秒）を床の 140/150 と
  max で。短文は従来とビット同一。
- SIDRA での反映先: C-1395（say() の読速床・判定器 creation_say_readable）
- SIDRA での反映先: C-1018（コントラスト・ドア標識・水配置）**→ 反映済み 2026-08-29（C-1018 完了: 壁に縁の形・扉にシェブロン・池を実配置）** / C-1019（仮想パッド、
  48dp 以上・reduced-motion と両立）**→ 反映済み 2026-08-29（C-1019 完了: 56px の
  ボタンを 12px 間隔で canvas 内に描画。合成 KeyboardEvent でテンプレ側の
  キーボード処理をそのまま駆動するので、新テンプレは書いた日から指で遊べる）**

## 5. 収集要素には使い道（シンク）が必須

- 出典: https://www.gamedeveloper.com/design/opinion-collectible-intent ・
  https://game-wisdom.com/critical/collectible-design-videogames ・
  https://300mind.studio/blog/what-is-game-economy-design/（いずれも 2026-08-29 確認）
- 事実: 収集物に意味のあるゲーム内目的が無ければ、プレイヤーは収集物どころか
  ゲーム自体への興味を失う。経済設計では tap（資源の入口）と sink（出口）の
  釣り合いが基本。収集を始めさせるには資源やボーナス体力など外的動機が要る。
- 学び: SIDRA の宝石は tap だけあって sink が無い（数字が増えるだけ）。
  **最小の sink は「宝石 n 個でハート回復/最大+1」**。これだけで草刈りに理由が生まれる。
- SIDRA での反映先: C-1021（宝石の使い道）**→ 反映済み 2026-08-29（C-1021 完了: 祠で宝石 3 個 → 最大ハート +1。宝石は tap だけだったのが 2 か所の sink を持った）**

## 6. 巨大ボス演出の文法（社長提供の映像を全編視聴して抽出）

- 出典: 社長所有 DVD の私的視聴（2026-08-31、『スター・ウォーズ／クローン・
  ウォーズ』の巨大生物回・22 分 29 秒を全編コマ送りで確認）。URL なし。
  以下は**映像の複製ではなく視聴して読み取った設計上の観察**。キャラ・名称・
  素材は C-0e 冒頭の決まりどおり生成物に使わない。
- 観察 1: **巨大さは「全身を見せない」ことで作られる。**怪獣は脚・尻尾・爪が
  画面を横切る部分描写が基本で、全身の引きは要所に 1 回だけ。小さい存在
  （兵士・戦車）と同じフレームに入れて対比する。カメラは低い。
- 観察 2: **重さは歩幅と土煙。**多脚戦車は脚の周期が遅く、接地のたびに土煙。
  被弾は「閃光 1 拍 → 煙が残る → シルエットが煙から再登場」の 3 段。
- 観察 3: **エスカレーションの型**: 作戦説明（ホロ卓）→ 部隊前進 → 予期せぬ
  覚醒（地割れが走る→兵が走って逃げる→塵の壁に呑まれる）→ 引きの 1 枚で
  規模提示 → 反応ショット（操縦席の顔）を挟んで再加速。
- 観察 4（実測）: **戦闘の音圧は平常より段違いに高い。**20 秒窓の平均ラウド
  ネスを全編測ったところ、戦闘窓は -13.8〜-16.5 LUFS に集中し、会話場面より
  明確に大きい。ゲームでも「戦闘中は音の密度を上げる」は音量差で作れる。
- 学び: SIDRA には**ボス戦という概念が無い**（敵は等身大の量産型のみ）。
  部分描写・遅い周期・土煙・段階（phase）・反応の間、は全部いまの canvas
  技術で再現可能。ブリーフィング（ホロ卓）は開始画面の強化形。
- 定量（2026-08-31 追加・**0.1 秒ごと全 13,487 コマを機械走査**して抽出。
  カット検出はコマ間輝度差分の突出、閃光は輝度の急騰と復帰で定義）:
  - カット数 308 / 22.5 分（平均ショット長 4.4 秒）
  - **戦闘のショット長 中央値 2.1 秒、会話 4.4 秒**——戦闘はカットが 2 倍速い。
    ゲームでは「戦闘中はイベント（攻撃・予兆・被弾）の間隔を約 2 秒に刻む」が
    このリズムの移植になる
  - **閃光は 13 回、半減まで中央値 0.20 秒**——SIDRA の現行 flash 減衰
    （1 フレーム 0.05、60fps で半減 0.17 秒）は**実測とほぼ一致**。既存値を
    根拠づける実測が取れた（変更不要）
  - **コマ間の動きは戦闘が会話の 2.9 倍**——C-1034 の音圧差と合わせ、
    「戦闘は音も動きも約 3 倍」が演出の基準値
  - 動き最大の 2 点はタイトルロゴとエンドロール（文字スクロール）で、
    ゲーム設計には非該当と判定
- SIDRA での反映先: C-1032（巨大ボステンプレ）/ C-1033（作戦説明つき開始画面）/
  C-1034（戦闘時の音圧差）**→ 反映済み 2026-08-30（ループA が 3 件とも完了:
  kaiju テンプレ＝7 本目・全 7 テンプレにブリーフィング開始画面・戦闘中の
  音圧段上げ。実測値 2.1 秒間隔／閃光半減 0.2 秒／戦闘 3 倍はそのまま採用された）**

## 7. グラフィックと構成（同映像の第 3 弾: 配色と場面の組み立てを機械抽出）

- 出典: §6 と同じ社長所有 DVD の私的視聴（2026-09-01 追加分析。社長指示

  45 秒間隔の全 30 場面から代表 10 場面を選び、各フレームの**主要 4 色を
  MEDIANCUT 量子化で機械抽出**した。以下は色の数値と設計上の観察のみで、
  映像の複製は含まない。

## 10. ブラウザ内 BGM ループ（外部調査 2026-09-03・辛口クリエイターループ）

SFX は §2 で解決済みだが、BGM の基準がどこにも無かったので増築。
URL はすべて 2026-09-03 に実際に開いて確認。

- 事実 1: **Web Audio の正確な音楽スケジューリングは「2 つの時計」方式。**
  JS のタイマだけでは layout・GC で数十 ms ずれる。低精度な JS 側ループ
  （25ms 間隔が例）で `nextNoteTime < currentTime + 先読み 0.1s` の間だけ
  ノートを予約し、実発音は AudioContext の高精度クロックに任せる。
  （出典: https://web.dev/articles/audio-scheduling Chris Wilson「A Tale of
  Two Clocks」）
- 事実 2: **レトロ・アーケードの BGM は 4〜8 小節の短いフレーズの反復。**
  メロディとベースの 2 トラック分離が基本で、著者のデモはベースを
  「周波数比おおよそ 1:4」（≒2 オクターブ下）に置いて濁りを避ける。
  ML 系（Magenta 等）は譜面生成に使えるが外部モデルが要る。
  （出典: https://abagames.github.io/joys-of-small-game-development-en/procedural/sound.html）
- 事実 3: **メジャー・ペンタトニック（長音階の 1,2,3,5,6）は半音もトライ
  トーンも含まないため、どの音を並べても和声的な失敗がほぼ起きない。**
  初心者の即興教育（Orff/Kodály）で使われる理由がそれ。
  （出典: https://en.wikipedia.org/wiki/Pentatonic_scale）
- 学び: SIDRA の 10 型は SFX・戦闘音圧差（§6 観察 4）まで持ちながら
  **BGM が 1 小節も無い**。§1 の技法列挙は「効果音と音楽」なのに半分しか
  実装されていない。上の 3 事実で「外部ファイル・外部モデルなしの安全な
  自動 BGM」は成立する: 依頼シードからペンタトニックの 4 小節 2 トラック
  （ベースは約 1:4 下）を決定論で編み、rAF を JS 側時計にした先読み予約で
  鳴らす。M ミュートと戦闘音圧差は SFX と同じ規則に従わせる。
- SIDRA での反映先: C-1304（全型 BGM ループ）
- 事実 4（増築 2026-09-05・辛口クリエイターループ。URL は同日に実際に開いて
  確認）: **音楽は状態遷移に反応するのが定石（adaptive music）**——戦闘の
  出入り・場所の変化・メニュー・**節目**で切り替える horizontal
  re-sequencing が基本技法で、最古参の例からそうなっている（Frogger は
  安全地点に着いた瞬間に音楽が切り替わる、Space Invaders はテンポが
  状況で変わる）。つまり「区切りが来ても同じループが流れ続ける」は
  この分野の反例そのもの: 終わりの画面は静で、そこに残る音は結末の
  ビート（勝利・敗北）だけであるべき。
  （出典: https://en.wikipedia.org/wiki/Adaptive_music）
- SIDRA での反映先: C-1336（区切りでは音楽も止まり、再開で戻る）

## 11. 自分と競わせる・難度を寄り添わせる（外部調査 2026-09-03・進捗監視ループ）

- 事実 1: **ゴースト（過去の自分の走りの再生）と競うと、単独プレイより努力量が増える。**

## 12. 入力の寛容さ（外部調査 2026-09-03・辛口クリエイターループ）

コヨーテタイム（§11 でも触れた）は実装済みだが、対になる先行入力の基準が
無かったので増築。URL は 2026-09-03 に実際に開いて確認。

- 事実 1: **Celeste の「許し」の設計**（Maddy Thorson 本人のスレッドの報道）:
  コヨーテタイム・**ジャンプバッファ（着地の少し前に押して押しっぱなしに
  すると、着地したまさにそのフレームで跳ぶ）**・頂点での半重力・角の
  自動補正など、全部が「タイミングと位置の窓を少しだけプレイヤー有利に
  広げる」哲学の実装。難しいのに優しく感じる理由がこれ。
  （出典: https://gigazine.net/gsc_news/en/20200317-celeste-action-feel-things/）
- 事実 2: **具体値**: ジャンプバッファは約 4 フレーム（60fps で 67ms）の
  保持が定番で、成功率 78%→99.2% の報告。コヨーテは 6 フレーム（100ms）が
  最適とされ、人間の反応時間に一致。両方とも「見えない補助」——
  プレイヤーは「ちゃんと押せた」と感じる。
  （出典: https://www.mygamedesign.com/what-makes-jump-mechanics-feel-responsive-and-satisfying/）
- 学び: SIDRA の platformer はコヨーテ 6f と可変ジャンプを持つが、
  **バッファが無い**——着地の 1〜2 フレーム前に押したジャンプは黙って
  捨てられ、次の足場で跳べずに落ちる。片方だけの実装は §12 的には半分。
  バッファは「押して保持したまま着地」でのみ発火させる（離したら破棄）と、
  可変ジャンプ（早離しで低く）と矛盾しない。
- SIDRA での反映先: C-1310（platformer のジャンプバッファ）**→ 反映済み 2026-09-03 15:05 UTC（C-1310 完了: `creation_jump_buffer` unmeasurable→1。BUFFER=5f、押して保持したまま着地したフレームで発火し、離せば破棄——可変ジャンプ（早離しで低く）と両立する。空中での即ジャンプは従来どおり無い。probe が実際に跳んで hard 含め確認、破壊 2 通りで計器 0）**
- 事実 3（増築 2026-09-04・辛口クリエイターループ。URL は同日に実際に
  開いて確認）: **押しっぱなしの移動は keydown の中で動かすのではなく、
  押下状態のフラグ（keydown で true・keyup で false）を持ち、毎フレームの
  ループ側でフラグを見て動かす**のがブラウザゲームの定石。MDN のゲーム
  制御機構の章がこの形（rightPressed/leftPressed を draw() 内で参照して
  playerX を毎フレーム加算）を明示的に推奨している。keydown イベント内
  だけで動かすと、連続移動が OS のキーリピート（初回 ~500ms の遅延＋
  機種依存の間隔）任せになり、リピートを合成しない入力装置——SIDRA の
  タッチパッドはまさに 1 押下 = keydown 1 回・離し = keyup 1 回——では
  押しっぱなしが 1 歩で止まる。
  （出典: https://developer.mozilla.org/en-US/docs/Games/Techniques/Control_mechanisms/Desktop_with_mouse_and_keyboard）
- SIDRA での反映先: C-1328（catch の押しっぱなし移動——10 型で唯一の
  keydown 刻み移動をフラグ＋毎フレームに）**→ 反映済み**
- 事実 4（増築 2026-09-08・辛口クリエイターループ。URL は同日に実際に
  開いて確認）: NN/g ユーザビリティ 10 原則の**第 5 原則 Error
  Prevention**——「the best designs carefully prevent problems from
  occurring in the first place. Either eliminate error-prone conditions,
  or check for them and present users with a confirmation option before
  they commit to the action.」エラーは slips（不注意の無意識エラー）と

  第 3 原則も Undo/Redo と明確な出口を求める。
  （出典: https://www.nngroup.com/articles/ten-usability-heuristics/）
- 学び: SIDRA の R は走行中でも**即時全消し**。キーボードの R は意図的な

## 13. リスクリワードとコンボ（外部調査 2026-09-03・進捗監視ループ）

- 事実 1: **リスクリワードは「通常要求を超えるリスクを取った者に報いる」

## 14. 効果音の反復変化（外部調査 2026-09-03・辛口クリエイターループ）

§2 は「合成できる」までで、「繰り返しに耐える」の基準が無かったための
増築。URL は 2026-09-03 に実際に開いて確認。

- 事実 1: **頻出 SFX は毎回わずかにピッチをランダムシフトすると
  「気づかれないほど自然な変化」になり反復感が消える**（銃声・足音の
  例。同じ音の連打は "painfully repetitive"）。半音＝×2^(1/12)≈1.06 が
  「上昇/下降列の自然な 1 段」で、ランダムシフトはそれより控えめが前提。
  応用 3 形: ランダムシフト／連鎖アクションでの上昇列／ピッチで強さや
  速さを伝える「情報としてのピッチ」。
  （出典: https://www.gamedeveloper.com/audio/the-power-of-pitch-shifting
  George Prosser, 2017-01-02）
- 事実 2: **変化幅は「ごく小さく」が正解で、大きいと不自然に刺さる**。
  ピッチ・音量の微小ランダム化＋直前と同じバリエーションを引き直す
  「連続同一の回避」の組み合わせが対話的音響の基本形。
  （出典: https://andrewmushel.com/articles/sound-effect-variation-in-unity/）
- 学び: SIDRA の SFX_TABLE は全 12 音が毎回**完全に同一の周波数**で鳴る。
  catch の連続受け・shooter の連射・step の足音は §2 の合成品質が
  あっても機械の反復に聞こえる。半音（6%）未満の ±4% ジッタを
  f0/f1 の両端に掛ければ、スイープの形（＝情報としてのピッチ、事実 1 の
  第 3 形）を保ったまま反復感だけが消える。BGM の音階は調律そのもの
  なので触らない。ゲームの盤面を配る seeded rand も消費しない
  （Math.random。盤面の再現性と無関係な層）。
- SIDRA での反映先: C-1317（SFX ピッチジッタ）

## 15. 明滅の安全上限（外部調査 2026-09-04・辛口クリエイターループ）

§4 は「明滅と反復パターンを避ける」までで、**何回までなら安全か**の

- 事実 1: **WCAG 2.3.1「3 回の閃光、または閾値以下」**: コンテンツは

  反対方向の変化の対」で、輝度差 10% 以上（暗い側が相対輝度 0.80 未満）
  が一般閃光。閃光が引き起こすのは偏頭痛・めまい・吐き気・光感受性
  発作。（出典: https://www.w3.org/WAI/WCAG21/Understanding/three-flashes-or-below-threshold.html）
- 事実 2: **面積の免除は視野 10 度の 25% まで**（典型視距離で約
  341×256 CSS px の矩形が視野 10 度に相当）。つまり全画面オーバーレイ
  （SIDRA の 720×320 の白フラッシュはこの矩形を超える）は回数制限側で
  守るしかない。（出典: 同上）
- 学び: duel は発射×2 者＋被弾の 3 箇所が全画面 α0.5 白の flash=1 を

  §1 の正解でも、**発火頻度に共有の門番が無い**のが欠陥。onset を

## 16. 触覚フィードバック（外部調査 2026-09-04・進捗監視ループ）

§1 の Juice は画面と音の 2 感覚まで。スマホ実機の品質を辛口ユーザーが
3 巡（C-1229/C-1234/C-1239）で押し上げている今、**触覚だけが未接続**の

- 事実 1: **`navigator.vibrate()` は外部ライブラリ不要の 1 行 API**。

  仕様側に織り込まれている）。（出典:
  https://developer.mozilla.org/en-US/docs/Web/API/Vibration_API）
- 事実 2: **対応は Android Chrome のみ、iOS Safari・デスクトップ

  設計できず、触覚を前提にした情報伝達（触覚でしか知らせない警告等）は

## 18. スマホの実画面面積（外部調査 2026-09-04・進捗監視ループ）

§4 は「読める画面」、C-1234 は「押せる大きさ」まで。**そもそもの
遊び面の広さ**を扱った節が無かったための増築。canvas は 720:320 の
横長比を保って縮むため、縦持ち 390px 幅の実プレイ面は 390×173 CSS px
——回転すれば 2 倍強になるのに、ページは何も促さない。URL は
2026-09-04 に実際に開いて確認。

- 事実 1: **向きの検出は CSS だけでできる**——`@media (orientation:
  portrait)` / `(orientation: landscape)` がレイアウト適応の推奨手段で、
  JS 側には `screen.orientation` の change イベントもある。ゲームは
  好みの向き（多くは landscape）へ `screen.orientation.lock()` で固定
  できるが、lock は Promise を返し失敗し得る（実装依存）ので、失敗を
  無害に飲む設計が前提。（出典:
  https://developer.mozilla.org/en-US/docs/Web/API/CSS_Object_Model/Managing_screen_orientation）
- 事実 2: **Fullscreen API（`element.requestFullscreen()`）は現行の
  Android Chrome/Firefox とデスクトップで対応済み**。iOS Safari は
  長らく部分対応（26.6 で全対応）なので、ボタンは対応検出つきの
  進歩的付加として置き、非対応では出さないか無害に退く。（出典:
  https://caniuse.com/fullscreen 2026-09-04 確認）
- 学び: SIDRA の生成ゲームは orientation/fullscreen への言及が 0 件
  （creation 配下 grep 0 件）。縦持ちで遊び始めた人に「回すと広い」を
  一言も伝えず、URL バーと余白に画面の 4 割を渡したままにしている。
  §17 のアトラクトモードで初見の 1 秒を作ったのだから、その 1 秒の
  画面が最大である価値は上がっている。条件: 促しは**案内であって
  遮断ではない**（縦のままでも遊べる・タップ主体の型では出さない判断も
  あり）、fullscreen は**利用者の押下でのみ**入る（勝手に全画面化は
  §4 の「読める画面」以前の礼儀違反）。
- SIDRA での反映先: C-1415（縦持ちへの回転の促し）**反映済み**・C-1416
  （全画面ボタン）**反映済み**
- C-1415 の実装メモ: 条件は `@media` ブロックではなく `matchMedia` で
  読む。事実 1 が薦めるのは CSS だが、項目の条件③「ゲーム中には出さない」
  は media 条件ではなく、1 つの要素の表示を 2 つの機構が決めると必ず
  食い違う。media query 自体は同じものを購読し、change を聞くので回転への
  即応（CSS なら只で手に入るもの）は保つ。②「タッチ非対応では出さない」は
  `(pointer: coarse)`——縦長のデスクトップ窓も portrait なので、これが
  無いと「モニタを回せ」と言う。判定器 creation_rotate_hint は縦持ち・
  横持ち・マウスの 3 通りで実走行し、走行中に画面を回して追従も見る。
- C-1416 の実装メモ: 全画面にするのは canvas ではなく canvas を包む
  `#stagewrap`——canvas 自身が画面いっぱいになると戻る手段が画面から
  消える。対応検出は `fullscreenEnabled`（iOS 向けに webkit 版も）で、
  既定は非表示・スクリプトが出す進歩的付加。事実 2 が前提とする「拒否を
  無害に飲む」は、判定器が node の unhandledRejection を監視して実測する
  ——書いてあるが素通りしている `.catch` と区別できるのはこれだけで、
  拒否走行 2 件・無拒否走行 0 件を数えて「常に増える定数」でないことも
  見ている。事実 1 の向き lock は全画面に入った後だけ試み、失敗は無視。
  項目に無かった修正 1 件: 押下後に `blur()`——SPACE は 4 型で「撃つ」
  なので、ボタンがフォーカスを持ったままだと発射が全画面切替になる。

## 21. ミキシング——重い一発の下で音楽が場所を空ける（外部調査 2026-09-06・辛口クリエイターループ）

§2 は合成・§10 は BGM・§14 は反復まで来たが、**重なったときの譲り合い**
（ミキシング）の基準が無かったための増築。URL は 2026-09-06 に実際に
開いて確認。

- 事実 1: ダッキング＝「他の信号の存在によってある信号のレベルを下げる」
  サイドチェイン技法。ゲームでは「その瞬間プレイヤーに聞かせるべき最重要の
  音」のために使う。**使いすぎ・掛けすぎは聴き手の気を散らす**——他の
  ミキシング手法と併用する 1 つの道具に留めること。
  （出典: https://www.asoundeffect.com/game-audio-mixing-demystified/）
- 事実 2: Quarles の実例（Fracture）: 台詞トリガで台詞以外を **-9dB へ
  500ms で下げ、台詞終了後 1000ms で戻す**。「思慮深く使えばゲームの物語を
  音で語る道具になる」。
  （出典: https://www.gamedeveloper.com/audio/game-audio-theory-ducking
  Zachary Quarles, 2009-01-29）
- 学び: SIDRA に台詞は無いが、台詞に当たる「その瞬間の最重要音」は
  勝利フレーズ（C-1326）・敗北ノイズ・節目の powerup（C-1346）。現状は
  4 小節ループが同じゲインのまま上に重なり続けていた。-9dB≈×0.355、
  保持は効果長ぶん、解放 ~1 秒——数字は事実 2 の実装値をそのまま借りる。
  乱発防止（事実 1）は「呼び出し側を重い 3 声に限る」設計で担保する。
- SIDRA での反映先: C-1371（MUSIC_DUCK・musicDuck()・判定器
  creation_bgm_ducking）

## 22. フォーカス喪失と入力の固着（外部調査 2026-09-06・辛口クリエイターループ）

§4 は「押せる・読める」まで、§12 は「押した意図を汲む」まで、§8 事実 5 は
「満員の乗り物で片手」のモバイル文脈まで来たが、**途中で離れた（alt-tab・
着信・ホーム画面）ときに入力状態がどうなるべきか**の基準が無かったための
増築。URL は 2026-09-06 に実際に開いて確認。

- 事実 1: **フォーカス喪失中に離された キーの keyup は届かない。**キーを
  押したまま別ウィンドウへ切り替えて離すと、押下状態は押されたまま残り、
  戻った後も「押しっぱなし」として動き続ける（stuck keys）。Emscripten の
  GLFW 移植に対する報告そのままで、報告者の提案は「**onblur を受けたら
  すべての入力状態（キーボード・マウス・その他）をリセットする**」。
  Emscripten 側は wontfix＝**アプリ側が自分で解くべき問題**として残った。
  （出典: https://github.com/emscripten-core/emscripten/issues/5122）
- 事実 2: **blur と hidden は別物。**onblur/onfocus はウィンドウ切替を
  教えるが、ページが隠れたとは限らない（別ウィンドウにフォーカスが移って
  も見えたままのことがある）。ページが隠れるのはタブ切替・最小化のとき
  で、それは visibilitychange / document.hidden が教える。MDN は隠れた
  ときの用途として動画・カルーセル・ポーリングの停止と**音を消す**ことを
  挙げる。（出典: https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API）
- 学び: 2 つの信号は役割が違う——**入力の解放は blur で**（見えていても
  フォーカスの無いページに keyup は来ないから。事実 1）、**進行と音の
  停止は hidden で**（見えたままのページを止めない。事実 2）。SIDRA は
  進行側を C-1450（不在時間は課金しない）で既に持つが、入力側が丸ごと
  無い: 全テンプレが押下フラグ（§12 事実 3 の定石形）を持ち、blur を
  誰も聴いていないので、→ を押したまま離れると戻った後も走り続ける。
  解放は「握られている物理キーぶんの合成 keyup を通常の配線に流す」形が
  よい——テンプレ 10 本の私有 keys を直接触らず、remap の翻訳（C-1305）
  も自然に通る。
- SIDRA での反映先: C-1373（blur/hidden での握りキー解放・判定器
  creation_focus_release）

## 23. permanence——結果は消えずに残る（外部調査 2026-09-07・辛口クリエイターループ）

§1 の Juice は「打った瞬間」の増幅（shake・hitstop・burst・flash）まで
で、**その後**——倒した敵・壊した物がどうなるか——の基準が無かったための
増築。URL は 2026-09-07 に実際に開いて確認。

- 事実 1: Vlambeer の Jan Willem Nijman『The Art of Screenshake』の技法表
  には screen shake・knockback・sleep(hitstop) 等と並んで **permanence**
  が独立の 1 項目としてある（13:18。27:54 には「even more permanence
  (smoke in explosion)」——爆発の煙まで残す追い足し）。
  （出典: https://theengineeringofconsciousexperience.com/jan-willem-nijman-vlambeer-the-art-of-screenshake/）
- 事実 2: その中身の定義: 「**Add permanence! Explosion, debris, enemy
  corpses, smoke, blood, destroyed objects, etc. Show the player the
  consequences of their actions.** Make them feel like they're
  interacting with the game world.」——薬莢は床に落ちて残り、倒した敵は
  離れて戻ってきてもまだそこにいる。結果が残ることが「世界に触っている」
  感触を作る。（出典: https://gamedevacademy.org/game-feel-tutorial/）
- 事実 3（増築 2026-09-07・辛口クリエイターループ。事実 1 と同じ
  技法表ページを同日に再確認）: 表には撃つ側の項目も独立にある——
  「Gun delay & kickback animations [19:52-20:23]」（発射の反動）と
  「Camera kick [25:09]」。撃った瞬間の体の反動は、当たった瞬間の
  knockback（17:15）と別の項目として数えられている。
  （出典: https://theengineeringofconsciousexperience.com/jan-willem-nijman-vlambeer-the-art-of-screenshake/）
- 事実 4（増築 2026-09-07・辛口クリエイターループ。事実 1 と同じ技法表
  ページを同日に再確認）: 弾の視覚は連続する 3 項目で並ぶ——「bigger
  bullets [10:13]」「**muzzle flash [10:39]**」「faster bullets
  [10:58]」。銃口の閃光は反動（19:52）とも弾そのものとも独立の 1 項目で、
  発射の**瞬間**を銃口の位置で光らせる。SIDRA は弾（3×10/4×10）・反動
  （C-1380）・軌跡（C-1389）まで持つが、銃口では何も光らない。
  （出典: 同上）
- 学び: SIDRA の Juice は瞬間側が完備（C-1032〜/C-1105/C-1343…）だが、
  **撃破の 0.5 秒後には何も無かったことになる**——shooter の敵は
  `hp>0` の filter で撃破フレームに配列から消え、adventure の敵は
  `alive=false` の瞬間から描画がスキップされる。burst の粒が消えたら
  戦いの痕跡ゼロ。最小の反映は (a) adventure: 倒した敵の場所に残骸を
  部屋に居る限り（再入室でも）描き続ける——`enemies[room]` は
  alive=false のまま保持されているので、描く側を足すだけで Nijman の
  「戻ってきてもまだそこにいる」がそのまま成立する。(b) shooter:
  撃破で機体色の破片が尾を引いて落ちる（薬莢の移植——宇宙に床は無い
  ので、残ることではなく**落ちて視界を横切ること**が痕跡になる）。
  残骸は静的な結果であって動きの装飾ではないが、落下・回転する破片は
  motion なので REDUCED では積まない（adventure の静止残骸は常に描く）。
- SIDRA での反映先: C-1374（adventure の残骸・shooter の破片・判定器
  creation_permanence）

## 24. 文字サイズの床（外部調査 2026-09-07・辛口クリエイターループ）

§4 はコントラスト（WCAG 4.5:1）・C-1234 は押せる大きさ（48dp）・§18 は
遊び面の広さまで来たが、**描かれる文字の大きさそのもの**の床が無かった
ための増築。URL は 2026-09-07 に実際に開いて確認。

- 事実 1: ゲームアクセシビリティガイドラインの基本項目に「読みやすい
  既定文字サイズ」があり、定量の参照値として「Amazon TV have
  10-foot-UI guidelines that include text size recommendations, of
  **28px minimum when viewed on a 1080p screen**」を挙げ、「**use 28px
  as a minimum rather than a target, aim to exceed it wherever
  possible**」と言う（弱視はこの床でも読めないので超えるほど良い）。
  1080p 基準の相対床＝画面高の約 2.6%。
  （出典: https://gameaccessibilityguidelines.com/use-an-easily-readable-default-font-size/）
- 事実 2: iOS の型スケールは **Caption 2 = 11pt が最小**（既定設定。
  Body は 17pt/行送り 22pt）——システム全体で 11pt を下回る型が存在
  しない＝プラットフォームの実質的な床。
  （出典: https://codershigh.github.io/guidelines/ios/human-interface-guidelines/visual-design/typography/index.html）
- 学び: SIDRA の canvas は 720 設計幅が CSS で縮む（§18）ので、床は

  床 11pt を上回るが、**11px は実効 10.2px で床を割り、12px は 11.1px
  で余白 1% しかない**。現物 census: cx.font 32 箇所中 13px が 18・
  20px が 8・16px が 2、そして **11px が 3・12px が 4**（adventure の
  石碑・duel の相手ラベル・platformer のランプ価格・round の履歴・
  startscreen の操作 2 行——後 2 者は共有プリアンブルで全 10 型に載る）。
  床は「canvas 描画文字 ≥ 13px（720 基準）」——18 箇所の事実上の標準と
  同値で、最小横持ちでも iOS の床の上に立つ。DOM 側（調整パネル等）は
  canvas と違い縮まないので対象外。
- SIDRA での反映先: C-1375（7 箇所を 13px へ・判定器

## 25. 速度は連続音で聞かせる——エンジン声（外部調査 2026-09-07・辛口クリエイターループ）

§2 は単発の合成・§10 は BGM・§21 は譲り合いまで来たが、**ゲーム状態を
連続的に鳴らす声**（エンジン音＝速度の可聴化）の基準が無かったための
増築。URL は 2026-09-07 に実際に開いて確認。

- 事実 1: **最初期のレースゲームのエンジン音は「RPM が矩形波のピッチを
  駆動する」だけの実装**で、「An increase in RPM meant an increase in
  the pitch of the engine note and, **even at this basic level,
  communicated to the player their current speed**」。音は「エンジンの
  唸りの力と激情を、速度の純粋な表現と感覚としてスピーカーから直接
  プレイヤーの脳へ渡せる」——視覚では不可能な伝達。ただし**劇的に
  ピッチを振ると合成臭が出る**（当時のタイトルの識別点）。
  （出典: http://blog.lostchocolatelab.com/2012/05/racing-game-sound-study.html）
- 事実 2: ピッチシフト・ループは**最も単純で処理も容量も最小の技法**。
  代償は不自然さで、「**samples can start to sound stretched if you
  pitch them up or down further than 500 RPM**」＝振り幅は控えめに保つ。
  ミキシングはスロットルを離したら「**drop the Engine layer by a few
  dB off throttle**」——減速は音量も少し下がる。
  （出典: https://www.boomlibrary.com/blog/the-car-engine-sound-primer-mike-caviezel/）
- 学び: SIDRA の racing は離散 sfx 3 種（衝突・ラップ・取得）だけで、
  **速度そのものが無音**——速度計バーは見なければ分からない。チップ風
  合成（§2）にはまさに事実 1 の「矩形波ピッチ駆動」が era-appropriate
  で、振り幅は 1 オクターブ程度に抑え（事実 1/2 の合成臭警告）、
  減速でピッチと一緒にゲインも下げる（事実 2）。連続音は M 消音・
  音量パネル・§21 のダッキングに従い、単発 sfx の下に置く（§21 の
  乱発警告の連続音版＝小さく敷く）。
- SIDRA での反映先: C-1378（racing のエンジン声・判定器
  creation_engine_voice。marble の転がり音は別の動詞なので将来候補）

## 26. 表示リフレッシュレートと時間の単位（外部調査 2026-09-09・辛口クリエイターループ）

§1〜§25 は「何を見せるか・聞かせるか」を扱ってきたが、**その速さが何で
測られているか**の基準がどこにも無かったので増築。URL は 2026-09-09 に
実際に開いて確認。丸写しはせず、要約と実測のみ。

- 出典: https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame
  （2026-09-09 確認）
- 事実 1: `requestAnimationFrame` のコールバック引数は
  `DOMHighResTimeStamp`＝**前フレームの描画終了時刻**であり、呼び出し頻度は
  **通常ディスプレイのリフレッシュレートに一致**する。MDN は「最も一般的なのは
  60Hz だが、**75Hz・120Hz・144Hz も広く使われている**」と明記する。
- 事実 2: 同ページは警告として、**「フレーム内でアニメーションがどれだけ進むかは
  必ず第 1 引数（または他の現在時刻の取得手段）で計算せよ——さもないと
  高リフレッシュレート画面でアニメーションが速く動く」**と書いている。
  つまり「1 フレーム＝一定時間」は仮定してよい前提ではない。
- 出典: https://gafferongames.com/post/fix_your_timestep/（2026-09-09 確認）
- 事実 3: 可変 delta time は**物理の挙動そのものをフレームレート依存にする**
  （手触りの差から、ばねの発散・高速物体の壁抜けまで）。標準解は
  **アキュムレータ方式の固定タイムステップ**——毎フレーム実経過時間を
  アキュムレータに足し、シミュレーションは一定 dt 刻みでだけ進め、
  端数は次フレームに持ち越して描画と切り離す。
- 事実 4: 更新が実時間に追いつかないと「死のスパイラル」に入る。対策は
  1 フレームあたりのステップ数に**上限を設ける**こと——負荷時は
  スパイラルではなく**スローモーションで劣化させる**、という設計判断。
- 実測（2026-09-09・SIDRA の実ページを node で駆動。rAF を 60/120/144Hz 相当の
  間隔で回し、**実時間 3 秒**ぶん進めて比較）:

  | 駆動レート | racing の走行距離（3 秒） | ラウンド時計 |
  |---|---|---|
  | 60Hz | 482.92 | 3000ms |
  | 120Hz | 832.64（**1.72 倍**） | 3000ms |
  | 144Hz | 929.84（**1.93 倍**） | 3000ms |

  **時計だけが正直だった。**`ROUND_MS` は実時刻の差分（C-1104 系）なので
  どのレートでも 3000ms を返すのに、世界の側は `dist+=spd` / `f.y+=f.vy` /
  `me.vy+=GRAV` / `s.y-=7` のように**フレーム 1 回＝1 単位**で進む。
  結果、120Hz の端末では同じ 60 秒に**約 2 倍の距離とほぼ 2 倍の敵**が来る。
- 学び: これは見た目の粗さではなく**公平性と再現性の問題**。SIDRA は
  「同じ依頼文＝同じ盤面」を seed で保証してきた（duel/shooter/racing の
  determinism 検査）が、その保証は**同じリフレッシュレートの端末どうしでしか
  成り立っていない**。§8 事実 5 の「満員の動く乗り物で片手」の相手は
  スマホであり、120Hz のスマホは 2026 年には珍しくない。
  §11（難度を寄り添わせる）で測ってきた難しさも、画面が速い端末では
  勝手に上がっている。
- 実装上の注意（この製品の事情）: 既存の probe と判定器は rAF を **16ms 刻み**で
  手回ししている。固定ステップの門は「16ms でも必ず 1 回進む」ように
  作らないと、数百本の既存検査が意味を変えてしまう。したがって
  しきい値は 1000/60 のちょうどではなく**わずかに下**に取り、端数は
  持ち越し・負なら 0 に丸める（事実 3 のアキュムレータの、この製品向けの形）。
- SIDRA での反映先: C-1607（共通の固定ステップ門と racing への適用）/
  残る 9 型への展開は後続サイクル（§7 観察 7 を 6 サイクルかけて配ったのと同じ進め方）

## 27. 横スクロールのカメラ（外部調査 2026-09-10・辛口クリエイターループ）

§1〜§26 は「何を見せるか」を扱ってきたが、**どこを見せるか＝カメラ**の基準が
どこにも無かったので増築。§1 の「揺れ」と §6 の「カメラは低い」に断片が
出てくるだけで、追従の設計は一度も書かれていない。URL は 2026-09-10 に実際に
開いて確認。丸写しはせず、用語と要点の要約と実測のみ。

- 出典: https://www.gamedeveloper.com/design/scroll-back-the-theory-and-practice-of-cameras-in-side-scrollers
  （Itay Keren「Scroll Back」GDC 2015 の記事版・2026-09-10 確認）
- 出典（存在確認のみ）: https://www.gdcvault.com/play/1022243/Scroll-Back-The-Theory-and
  （同講演・2026-09-10 確認）
- 事実 1（用語）: 2D カメラの追従には名前が付いている。
  **position-locking**（カメラを自機の位置に固定）/ **camera-window**（一定の
  枠内では動かず、枠を押した時だけスクロール＝不感帯）/ **lerp-smoothing**
  （毎フレーム線形補間で距離を詰める）/ **platform-snapping**（着地した時だけ
  寄せる）/ **forward focus（先読み）** / **camera-attractors**（注目物へ寄る）。
- 事実 2: **position-locking は「全方向に視界はあるが先読みが無い」**。
  記事は明確に、急な方向転換でカメラが急加速し、視覚と前庭感覚の衝突による
  不快を生むと指摘する。
- 事実 3: **camera-window（不感帯）は「何千もの後続プラットフォーマーの標準を
  作った」**が、前方視界が狭くなるという副作用を持つ。
- 事実 4: **lerp-smoothing は「最も効果的で普及した平滑化」**。速度がまちまちな
  動きに効く。ただし極端に速い時は迫る脅威を隠しうる。
- 事実 5: **先読みには 3 つの実装がある**——静的（進行方向へ固定量ずらす）/
  target-focus（入力の向きへずらす）/ projected-focus（速度から予測位置へ）。
- 実測（2026-09-10・SIDRA の platformer）: カメラは
  `cam=Math.max(0,Math.min(LW-W,me.x-260))` の**純粋な position-locking**。
  720px の画布で自機は常に x=260 に釘付けなので、**右へ走る時の前方視界は
  460px、左へ戻る時はわずか 260px**。しかも平滑化が無いので、方向転換した
  フレームに世界が瞬間的にずれる（事実 2 の不快そのもの）。
  灯籠まで歩いて戻る設計（C-1021 系）がある型で、戻る方向の視界が
  進む方向の 57% しかないのは非対称。
- 学び: 追従の設計は「固定か否か」ではなく**先読み量と平滑化の 2 つの数字**。
  SIDRA には両方とも無い。しかも**先読みの向きを表す信号は既にある**——
  `me.look`（C-1348 が顔のために入れた ±1）。
- SIDRA での反映先: C-1622（platformer に target-focus の先読みと lerp 平滑化）/
  racing・marble・shooter は自機が画面に固定される型なので別問題として保留

## 28. 聴覚のアクセシビリティ——音だけが知っている情報を作らない（外部調査 2026-09-10・辛口クリエイターループ）

- 出典: https://gameaccessibilityguidelines.com/full-list/（2026-09-10 に実際に
  開いて確認。§4 の「背景の動きを切るオプション」と同じ一覧の、Hearing/audio
  カテゴリ。丸写しはせず、該当ガイドラインの文言と水準のみ引用）
- 事実（Basic）: **「Ensure no essential information is conveyed by sounds
  alone」**——本質的な情報を音だけで伝えない。同じ Basic に「字幕を使うなら
  読みやすい形で」「効果音・音声・音楽の音量を別々に絞れる/消せる」がある。
- 事実（Intermediate）: **「Ensure that all important supplementary
  information (eg. the direction you are being shot from) conveyed by audio
  is replicated in text / visuals」**——音で伝える**補足**情報も、とくに
  **どちらの方向で起きたか**は、文字か絵に**複製**すること。同水準に
  「重要な環境音にも字幕か視覚表現を」がある。
- 学び: §4 は視覚側の同じ規則（**色だけで本質情報を伝えない**・形やパターンを
  併用）を最初から持っているのに、**聴覚側の対になる規則がどこにも無かった**。
  そして SIDRA は C-1394 で **定位（pan）という情報チャンネルを 10 か所に
  新設した**——つまり「どちら側で起きたか」を**耳に向けて**足した。
  Intermediate のガイドラインが例に挙げているのはまさにこれ（撃たれた方向）で、
  **足した以上は目にも同じことが見えていなければならない**。
  音量の別チャンネルと全体ミュートは調整パネルが既に持つ（§4 の第 3 チャンネル
  と同じ場所）ので、欠けているのは**耳と目が同じ場所を指しているか**の側。
- SIDRA での反映先: C-1650（racing のスリップストリーム——耳は障害物の x で
  鳴り、目は自機の x で弾ける。条件が |o.x-car.x| 26〜46px なので**必ず
  26px 以上ずれる**）／marble は同じ問題を先に正しく解いている（`gpan` は
  射影ではなくレーン位置、burst は同じゲートの `gx`——理由がコードに書いてある）
