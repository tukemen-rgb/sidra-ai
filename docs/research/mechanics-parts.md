# メカニクスの部品化: 何が実際に共有されているかを測った（C-1114, 2026-09-03）

§9 学び (3)（テンプレ N 種方式は 10 個目が 1 個目と同じだけ高い）に対する
先手として、「移動 / 衝突 / スコア / 敵行動を部品に分解し、組み合わせで
新ジャンルを出す」設計を検証した。**設計する前に、現状 9 テンプレが実際に
何を共有しているかを測った。答えは前提と違っていたので、そこから書く。**

## 1. 測定

9 テンプレの本体（合計 1024 行）を空白正規化し、25 文字以上・コメント以外の
行のうち **2 テンプレ以上に完全一致で現れるもの**を数えた。

| 出現 | 内容 | テンプレ |
|---|---|---|
| 9/9 | `const cv=document.getElementById('stage'),cx=cv.getContext('2d');` | 全部 |
| 7/9 | 種つき `rand()` の 1 行実装 | catch/fishing 以外 |
| 7/9 | HUD のフォントと色の設定（13px / 20px） | catch/fishing 以外 |
| 4/9 | `function step(){const now=performance.now();` | adventure/duel/platformer/shooter |
| 3/9 | `addEventListener('keydown',…)` の各綴り | 3 通りに分かれる |

**一致行は全部で 27 行しかない。** そして上位はすべて**基盤**であって
メカニクスではない。計画が名指しした 4 種のうち、そのまま持ち上げられる形で
重複していたのは **1 つだけ**だった:

**x 方向の操舵（端で止める）** — kaiju・racing・shooter・platformer の
4 テンプレが独立に書いている。違いは (a) キーの読み方の綴り、(b) 速度、
(c) 余白の 3 つだけ。つまり**引数**である。

```
platformer  if(K('ArrowLeft')){me.x=Math.max(10,me.x-RUN)}
shooter     if(keys['arrowleft']||keys['a']){ship.x=Math.max(SHIP,ship.x-4)}
racing      if(K('ArrowLeft'))car.x=Math.max(14,car.x-3.4);
kaiju       if(K('ArrowLeft'))me.x=Math.max(30,me.x-2.1);
```

## 2. 本当の障害（これが今回いちばん重要な発見）

残り 3 種（衝突・スコア・敵行動）が共有されていない理由は「まだ抽出して
いないから」ではない。**共有できる形になっていないから**である。

- **座標系が 2 つある。** `catch` と `fishing` は canvas に対する 0..1 の
  正規化座標で物を置く。残り 7 つはピクセル。落下物の衝突を 1 つの部品に
  するには、どちらかを書き直すか、呼び出しごとに境界で変換するしかない。
- **「世界の中の物」の形が揃っていない。** shooter の敵は
  `{x,y,vx,vy,r,hp}`、catch の落下物は `{x,y}`、platformer の宝石は
  `{x,y,got}`。3 つの形に対して衝突部品は書けない。
- **ループの形が 2 つある。** `catch` と `fishing` には `state` も
  `reset()` も無い。残り 7 つには両方ある。ラウンドを終わらせる部品は、
  前者に対して呼ぶ先が無い。

**したがって「部品を組み合わせて新ジャンル」は抽出作業ではなく、まず
契約（contract）を決める作業である。** 契約なしに部品を抜き出すと、
抜き出した元の 2 テンプレでしか使えない部品置き場ができる。

## 3. PoC: 契約を 1 つだけ決めて、2 テンプレを載せ替えた

`src/sidra_ai/creation/parts.py`。部品は 1 つ、呼び出しは 2 つ。

**入力の契約（今回決めたもの）**: 部品はキー状態を**ページ側**から読む。
テンプレ private の `keys` マップからは読まない——キーを private に持つ
テンプレは、そもそも他と組み合わせられない。別名（`ArrowLeft` / `a` 等）は
部品の引数として渡す。

```js
function partsSteerX(actor,speed,lo,hi,left,right){ … }
```

`racing`（速度 3.4・余白 14）と `kaiju`（速度 2.1・余白 30）を載せ替えた。
**キー・速度・余白は 1 つも変えていない**ので、これは純粋な差し替えである。

**載せ替えなかった 2 つと、その理由**（どちらも単純置換では済まない）:

- `shooter`: A/D も受けるので、載せ替えるとキーの意味が変わる。
- `platformer`: canvas 幅ではなく**レベル幅**で端を決めている。

未載せ替えを残したのは、同じツリーの中に「前」が残るからでもある。実測では
部品の移動回数が kaiju=170・racing=1629 に対し、shooter=0・platformer=0。
**部品が動かしていることが、部品を使っていないテンプレとの対比で見える。**

## 4. 判定

この項目の完了条件は「判定器の数字が落ちないこと」。載せ替え後、
`product_metrics.py --compare` は**どの数字も動かさない**（NO MOVEMENT）。
それが正しい結果である——**これはリファクタであって、外の誰かに届く変化では
ない。** 動いた数字が無いことを `[記録]` として残す。

## 5. 次にやるべき順序（この文書の本題）

1. **座標の契約**を決める（ピクセルに寄せる、が現実的: 7 対 2）。
   `catch` / `fishing` の書き直しは実プレイ判定器（C-1108 の初成功、
   C-1118 の全部入り）で守られている。
2. **エンティティの契約**を決める（`{x,y,r}` を最小、`vx,vy,hp` を任意）。
   ここまで来て初めて**衝突**が部品になる。
3. **ループの契約**（`state` と `reset()` を全型に）。これで**ラウンド・
   スコア・敵行動**が部品になる。
4. そこまでやって初めて「組み合わせで新ジャンル」が試せる。**1〜3 を
   飛ばして 4 をやると、部品ではなく 10 個目のテンプレが増えるだけである。**

各段階の条件は同じ: **既存の判定器の数字が 1 つも落ちないこと。**
