# セキュリティゲート 誤検知ベースライン（実データ測定）

v0.1 で唯一やり残していた「実データでの誤検知率測定」の結果。

## なぜ測るのか

誤検知が多いゲートは、運用側が「またか」と無視するようになる。無視された時点で
防御は存在しないのと同じになる。検知率だけでなく**誤検知率が運用上の生死を分ける**。

## 測定条件

- 対象: 許可済み5リポジトリ（site / creater-yard / Fg / marketing / sidra-ai）
- 母数: **1012 文書**（README・docs・ソース・直近コミットメッセージ）
- 判定: `SecurityGate.inspect` の decision が ALLOW 以外＝索引から外れる
- 測定器: `scripts/measure_gate_baseline.py`（値は一切出力せず、パス・行・種別のみ）

## 結果

| リポジトリ | 文書 | 修正前 | 修正後 |
| --- | ---: | ---: | ---: |
| site | 349 | 2.9% | **2.0%** |
| creater-yard | 167 | 5.4% | **3.0%** |
| Fg | 65 | 0.0% | **0.0%** |
| marketing | 68 | 11.8% | **0.0%** |
| sidra-ai | 363 | 6.3% | 6.3% |
| **合計** | **1012** | **4.9%** | **3.5%** |

測定時点の sidra-ai は 363 文書。その後 main が 333 コミット伸びて 491 文書に
なったため、現在の同条件の測定は合計 1140 文書 / 4.6% になる。母数が違うので
3.5% と 4.6% を直接比べないこと。検知器の変更を評価するときは、必ず**同一の
コミットで前後を測る**。

索引から外れた文書は 50 件 → **33 件**。

## 特定した誤検知

### 1. git 短縮 SHA を電話番号と誤判定（最大要因）

`phone_jp` の正規表現は「0 で始まる 6 桁以上の数字列」に一致していた。これは散文中の
git 短縮 SHA（`0965092`）とまったく同じ形。marketing で隔離された 8 文書は**全てこれ**。

日本の電話番号は 10 桁（固定・0120）か 11 桁（携帯）と決まっているため、桁数検証を
追加した。E.164 に従い国際番号は 9〜15 桁。

発火回数 22 → **5**。

### 2. TypeScript の型注釈を秘密の代入と誤判定

`token: string` `password: string` は宣言であって値ではない。`autocomplete="current-password"`
は入力欄の用途を示す標準属性で、漏洩とは逆の意味を持つ。creater-yard の認証ページ
（login / signup / reset / account）が全て隔離されていた。

型名と autocomplete トークンを除外値に追加。閉じ括弧も式の判定に含めた。

発火回数 22 → **5**。

## 判断を残した項目

### RFC 2606 予約ドメイン（`example.com`）

`placeholder="mail@example.com"` などの UI プレースホルダが個人メールとして
HIGH 判定され、site の 3 コンポーネントと設計文書が隔離されている。予約ドメインは
実在し得ないので誤検知である。

**ただし修正は見送った。** 既存の output guard テスト 5 件が `@example.com` を
「個人のメールアドレス」の代表値として使っており、変更するとその安全保証テストを
書き換えることになる。影響は 1012 件中 4 件（0.4%）で、テスト側の前提を触る
リスクに見合わない。テストのサンプル値を予約外ドメインに変える形で対応すべきだが、
それは output guard の担当者が判断すべき事項。

### `high_entropy` の発火過多 — 解消済み

**症状:** 1012 文書で 1018 回発火。ほぼ全文書で 1 回以上鳴り、MEDIUM のため
隔離はしないが監査記録が埋まって本当の検知が埋もれていた。

**原因:** 発火 3580 件を分類したところ **3539 件（98.9%）が `.json` データ
ファイル**だった。検索インデックス・ロックファイル・フィクスチャの類である。

閾値調整では直らない。ノイズ自体が本当に高エントロピー（5.2〜5.3 bit/文字）で、
閾値を上げると本物の認証情報のほうが先に落ちる。なお 16 進ダイジェストは
最大 4.0 bit/文字なので、そもそも閾値 4.2 に到達しない。

**採った解決策:** 密度で信号が反転することを利用する。散文中の 1 個は疑わしいが、
1 文書に 500 個あるならそれはデータセットである。1 文書あたり 5 件を超えたら、
個別に報告せず `high_entropy_dataset` として **1 件・LOW** にまとめる。
スパンの伏せ字は従来どおり全件に適用するので、索引に生の高エントロピー文字列が
入ることはない。

**効果（同一母数 1140 文書で前後比較）:**

| | 変更前 | 変更後 |
| --- | ---: | ---: |
| `high_entropy` 発火 | 1022 | **266** |
| 隔離された文書 | 51 | **51** |
| 全体の flag 率 | 4.6% | **4.6%** |

**判定は 1 件も変わっていない。**監査ノイズだけが 74% 減った。

### sidra-ai 自身の 6.3%

攻撃パターンを記述したセキュリティコードとそのテストが隔離されている。
**これは正しい挙動とも言える**が、結果として SIDRA は自分自身のセキュリティ実装を
検索できない。運用上どちらを取るかは要判断。

### 巨大 JSON（site の 2 件）

`data/games.json` と `data/search-index.json` がサイズ上限で BLOCK。データ配列であり
文書ではないので妥当だが、これらを検索対象にしたい場合は別経路が要る。

## 再現方法

```bash
python scripts/measure_gate_baseline.py \
  "tukemen-rgb/site=<path>" "tukemen-rgb/creater-yard=<path>" ...
```

値は出力されない。パス・行番号・検知種別のみが記録される。
